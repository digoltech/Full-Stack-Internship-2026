# 17.2 — Choosing a Component Library

**Goal:** Compare common React component systems and choose one based on the product, team, and design requirements rather than popularity alone.

## 1. The Main Trade-Off

A styled component library saves time by giving you ready-to-use controls and a visual system. The trade-off is that your product inherits conventions from that system and must learn its APIs and customization model.

Consider these questions before choosing:

1. Is this a data-heavy internal tool or a highly branded customer product?
2. Does the team need complete components, or only accessible interaction primitives?
3. How much time can the team spend on visual customization?
4. Does the library support the React version, framework, and browsers in this project?
5. Can the team maintain the dependency and upgrade it safely?
6. Does the library support required keyboard and screen-reader behavior?

## 2. Material UI (MUI)

MUI provides React components following Material Design conventions, along with a theming system. It can be a strong choice when its design language fits the product or when a team needs a broad set of consistent controls.

### Install

```bash
npm install @mui/material @emotion/react @emotion/styled
```

### Example

```jsx
import { Button, Card, CardActions, CardContent, Typography } from '@mui/material';

export function ProjectCard({ project, onOpen }) {
  return (
    <Card variant="outlined">
      <CardContent>
        <Typography variant="h6" component="h2">{project.name}</Typography>
        <Typography color="text.secondary">{project.description}</Typography>
      </CardContent>
      <CardActions>
        <Button onClick={() => onOpen(project.id)}>Open project</Button>
      </CardActions>
    </Card>
  );
}
```

The component receives data and an action through props. It does not own the whole project list or perform navigation by itself. That separation makes the card easier to test and reuse.

### Theme Provider

MUI themes are typically applied near the app root with `ThemeProvider` and `CssBaseline`. A theme centralizes design decisions; avoid redefining the same colors separately in every component.

## 3. React Bootstrap and Bootstrap CSS

Bootstrap is a CSS framework with a grid, utility classes, and a familiar visual language. React Bootstrap provides React components that follow Bootstrap patterns without requiring Bootstrap's jQuery-based JavaScript.

Install the packages when using React Bootstrap:

```bash
npm install react-bootstrap bootstrap
```

Import its stylesheet once in the app entry point:

```jsx
import 'bootstrap/dist/css/bootstrap.min.css';
```

Example:

```jsx
import Button from 'react-bootstrap/Button';
import Card from 'react-bootstrap/Card';

export function NoticeCard() {
  return (
    <Card>
      <Card.Body>
        <Card.Title>Profile saved</Card.Title>
        <Card.Text>Your profile changes are now available.</Card.Text>
        <Button variant="primary">View profile</Button>
      </Card.Body>
    </Card>
  );
}
```

Bootstrap can be useful for quick, familiar layouts. If using React Bootstrap, avoid also wiring Bootstrap's standalone JavaScript plugins to the same controls; two systems trying to control one dropdown or modal can cause bugs.

## 4. Chakra UI

Chakra UI is a React component system with theming and composable primitives. Its API and setup have changed across major versions, so follow the documentation matching the installed version rather than copying an example from an older tutorial.

Evaluate it for accessibility support, component coverage, theming, bundle impact, and compatibility with your styling approach. Do not mix examples from different major versions: provider setup and component APIs may differ.

## 5. Compare the Approaches

| Tool | Provides | Customization | Often a fit for |
| --- | --- | --- | --- |
| Ant Design | Broad styled React components and data-oriented controls | Theme tokens and component APIs | Admin tools and business dashboards |
| MUI | Broad styled components and a mature theme system | Theme and component styling APIs | Products where Material conventions fit |
| React Bootstrap | React components that follow Bootstrap patterns | Bootstrap variables and CSS | Fast, familiar responsive interfaces |
| Chakra UI | Styled, composable React components | Theme and component props | Teams that want a component-first workflow |
| Radix Primitives | Accessible interaction primitives, mostly unstyled | You build the visual system | Custom product design systems |
| shadcn/ui | Source components copied into your repository | You own the component source | Tailwind projects needing editable components |

This is not a quality ranking. Verify current maintenance, compatibility, accessibility behavior, and licensing for the exact packages you select.

## 6. Avoid These Common Mistakes

- **Installing several full UI systems:** This creates inconsistent controls and increases maintenance and bundle cost.
- **Assuming components guarantee accessibility:** Use labels, semantic HTML, visible focus, and keyboard checks.
- **Overriding internal CSS selectors:** Internal class names may change. Prefer supported theme APIs and documented props.
- **Choosing before prototyping:** Build one representative page with a form, a dialog, and a data table before committing.
- **Ignoring responsive behavior:** A desktop table or dialog may not work on a phone without an explicit design decision.

## 7. Decision Exercise

For each product, recommend one approach and give two reasons:

1. An internal inventory dashboard with filters, tables, and forms.
2. A branded event site with a unique visual identity and a small set of custom controls.
3. A prototype that must be built quickly with familiar responsive layouts.

There can be more than one defensible answer. Explain the trade-offs and name one risk you would verify in a prototype.
