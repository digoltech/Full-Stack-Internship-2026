# 17.3 — Headless Components, Radix, and shadcn/ui

**Goal:** Understand the difference between behavior and appearance, then decide when to use headless primitives or source-owned components.

## 1. What Does “Headless” Mean?

A headless UI tool provides behavior without prescribing a finished visual design. For example, an accessible dialog needs to manage focus, close on Escape, and keep keyboard navigation inside the dialog. A headless primitive can provide those behaviors while your app supplies the colors, layout, and typography.

This gives more visual control, but it does not mean “no work.” You still need to style the component, provide accessible labels, and test the interaction.

## 2. Radix Primitives

Radix Primitives are low-level React building blocks for common interactions. They are useful when you want documented behavior and accessibility support while retaining ownership of the visual design.

A dialog's conceptual structure looks like this:

```jsx
<Dialog.Root>
  <Dialog.Trigger>Open settings</Dialog.Trigger>
  <Dialog.Portal>
    <Dialog.Overlay />
    <Dialog.Content>
      <Dialog.Title>Settings</Dialog.Title>
      <Dialog.Description>Update your preferences.</Dialog.Description>
      <Dialog.Close>Close</Dialog.Close>
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
```

The exact package and API depend on the primitive and installed version. The important pattern is that the library manages interaction relationships while your CSS styles the parts. Always include a title and an accessible name, and verify focus behavior with a keyboard.

## 3. What Is shadcn/ui?

shadcn/ui is not a traditional component package where every component remains hidden inside `node_modules`. Its tooling adds selected component source files to your project, commonly built with Radix primitives and Tailwind CSS. You can then inspect, change, and maintain that source like your own code.

Typical setup (follow the current official instructions for your framework and package manager):

```bash
npx shadcn@latest init
npx shadcn@latest add button dialog
```

The generated files and configuration become part of your application. Commands and configuration options may change, so consult the current documentation rather than treating an old command as permanent.

### Advantages

- You can change component markup and styles directly.
- Components fit naturally into a Tailwind-based design system.
- You add only the components you choose.

### Responsibilities

- You own future modifications and should review changes during upgrades.
- You must keep dependencies and generated source compatible.
- You remain responsible for composition, accessibility, responsive design, and tests.

## 4. Package Component vs Source Component

| Question | Installed component package | Source copied into your project |
| --- | --- | --- |
| Where is implementation? | Usually in a package under `node_modules` | In your repository |
| How do updates arrive? | Package updates | You review and merge source changes |
| How much can you customize? | Through documented APIs and theming | Directly, with responsibility for the result |
| Best when | Standard behavior and centralized maintenance matter | Design control and local ownership matter |

Neither is automatically better. Consider how many developers will maintain the UI, how often designs change, and whether your team is prepared to own copied source.

## 5. Accessible Dialog Checklist

When building a dialog with any library, verify:

- It opens from a keyboard-operable control.
- Focus moves into the dialog when it opens.
- Tab navigation stays in the dialog while it is modal.
- Escape and a visible close control dismiss it when appropriate.
- Focus returns to the trigger after closing.
- The dialog has a meaningful title and description where helpful.
- The page behind it cannot be accidentally operated while it is modal.

A library can help implement these behaviors, but a quick keyboard test is still necessary.

## 6. Choosing an Approach

Use a styled library when you want complete controls and a shared visual system quickly. Use headless primitives when the design must be custom and the team can implement styling. Use shadcn/ui when its source-owned, Tailwind-oriented workflow matches your team's maintenance model.

## Key Terms

- **Primitive:** a low-level component used to compose a larger interface.
- **Focus trap:** keyboard focus is constrained within an active modal dialog.
- **Portal:** rendering content elsewhere in the DOM, often used for dialogs and menus.
- **Source ownership:** the application team can directly inspect and maintain component code.
