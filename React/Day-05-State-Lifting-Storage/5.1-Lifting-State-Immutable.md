#  — Day 5.1: Lifting State Up, Immutable Updates, localStorage and `useRef`

## 1. Learning Objectives

By the end of this session, students should be able to:

- Explain why two components sometimes need to share the same state.
- Lift state up to the nearest common parent component.
- Follow the rule "data flows down through props, events flow up through functions".
- Recognise prop drilling and explain why it becomes a problem.
- Distinguish between **state** and **derived data**, and avoid storing what can be calculated.
- Update arrays and objects in state without mutating them (add, remove, update, toggle, nested update).
- Persist state in `localStorage` using `useState` (lazy initialiser) and `useEffect`.
- Use `useRef` to access a DOM element and to store a value that does not trigger a re-render.
- Build a complete Task Manager from several cooperating components.

## 3. The Problem: Sibling Components That Need the Same Data

Imagine a shop page with two sibling components:

- `ProductCard` has an **Add to cart** button.
- `Navbar` shows the **cart count**.

```text
        App
       /   \
  Navbar   ProductCard
 (needs     (changes
  count)     count)
```

If `ProductCard` keeps `count` in its own `useState`, `Navbar` has no way to read it. In React, **siblings cannot read each other's state**. Data only travels in one direction: from parent to child, through props.

**The solution:** move the state to the closest parent that contains both components. This is called **lifting state up**.

## 4. Lifting State Up

### Step-by-step example: Cart count

```jsx
// App.jsx
import { useState } from "react";
import Navbar from "./components/Navbar";
import ProductCard from "./components/ProductCard";

function App() {
  // The state now lives in the common parent.
  const [cartCount, setCartCount] = useState(0);

  function handleAddToCart() {
    setCartCount((previousCount) => previousCount + 1);
  }

  return (
    <div>
      <Navbar cartCount={cartCount} />
      <ProductCard name="Wireless Mouse" price={799} onAddToCart={handleAddToCart} />
      <ProductCard name="Keyboard" price={1499} onAddToCart={handleAddToCart} />
    </div>
  );
}

export default App;
```

```jsx
// components/Navbar.jsx
function Navbar({ cartCount }) {
  return (
    <nav>
      <h2>My Shop</h2>
      <span>Cart: {cartCount}</span>
    </nav>
  );
}

export default Navbar;
```

```jsx
// components/ProductCard.jsx
function ProductCard({ name, price, onAddToCart }) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>₹{price}</p>
      <button onClick={onAddToCart}>Add to cart</button>
    </div>
  );
}

export default ProductCard;
```

### What happened?

1. `App` owns the state (`cartCount`).
2. `App` passes the **value** down to `Navbar` as a prop.
3. `App` passes the **function** down to `ProductCard` as a prop.
4. When the button is clicked, the child **calls** the function.
5. The function runs in `App`, state changes, and React re-renders `App` and its children.
6. `Navbar` receives the new `cartCount`.

### The golden rule

> **Data flows down (props). Events flow up (function calls).**

```text
  App  ── cartCount ──▶  Navbar
   ▲
   └── onAddToCart() ──  ProductCard
```

### How do I decide where state should live?

Ask three questions:

1. Which components **use** this state?
2. What is their **closest common parent**?
3. Put the state in that parent (not higher than necessary).

If only one component uses a piece of state, keep it inside that component. Do not lift state "just in case".

## 5. Prop Drilling

When state is lifted high up, you may need to pass props through components that do not use them just to reach a deeper component.

```jsx
function App() {
  const [user, setUser] = useState({ name: "Asha" });
  return <Layout user={user} />;
}

function Layout({ user }) {          // does not use user
  return <Sidebar user={user} />;
}

function Sidebar({ user }) {         // does not use user
  return <Profile user={user} />;
}

function Profile({ user }) {         // finally uses it
  return <p>Hello, {user.name}</p>;
}
```

`Layout` and `Sidebar` only act as pipes. This is called **prop drilling**.

| Situation | Is it a problem? |
|---|---|
| Passing props through 1–2 levels | Normal. Do not worry. |
| Passing through 3+ levels or many props | Hard to read and change. |

We will solve heavy prop drilling on **Day 9** with the Context API. For now, learn to recognise it.

**Alternative that often helps:** composition. Instead of passing data through layers, pass the finished element as `children` or a prop.

## 6. State vs Derived Data

**State** is data that changes over time and that you cannot calculate from anything else.

**Derived data** can be calculated from existing state or props during rendering.

### Bad: storing derived data in state

```jsx
function TaskApp() {
  const [tasks, setTasks] = useState([]);
  const [completedCount, setCompletedCount] = useState(0); // ❌ duplicate truth

  function toggleTask(id) {
    setTasks(/* ... */);
    setCompletedCount(/* easy to forget or get wrong */);
  }
}
```

Now two values must be kept in sync. Sooner or later they will disagree.

### Good: calculate while rendering

```jsx
function TaskApp() {
  const [tasks, setTasks] = useState([]);

  const completedCount = tasks.filter((task) => task.completed).length; // ✅
  const remainingCount = tasks.length - completedCount;                  // ✅

  return <p>{completedCount} done, {remainingCount} left</p>;
}
```

### Rule of thumb

Before creating a new `useState`, ask: **"Can I calculate this from state I already have?"** If yes, it is not state.

Typical derived values: totals, counts, filtered lists, formatted text, `isEmpty`, `isValid`.

## 7. Updating State Immutably

React decides whether to re-render by comparing the **old** state with the **new** state. If you change an array or object in place (mutation), the reference stays the same and React may not notice the change.

> **Never mutate state. Always create a new array or object.**

### 7.1 Arrays

| Goal | ❌ Mutating (do not use) | ✅ Immutable |
|---|---|---|
| Add | `tasks.push(x)` | `[...tasks, x]` |
| Add at start | `tasks.unshift(x)` | `[x, ...tasks]` |
| Remove | `tasks.splice(i, 1)` | `tasks.filter(t => t.id !== id)` |
| Update one | `tasks[i].title = "x"` | `tasks.map(t => t.id === id ? { ...t, title: "x" } : t)` |
| Sort | `tasks.sort(...)` | `[...tasks].sort(...)` |
| Reverse | `tasks.reverse()` | `[...tasks].reverse()` |

```jsx
// Add
setTasks((prev) => [...prev, newTask]);

// Remove
setTasks((prev) => prev.filter((task) => task.id !== id));

// Toggle completed
setTasks((prev) =>
  prev.map((task) =>
    task.id === id ? { ...task, completed: !task.completed } : task
  )
);

// Edit title
setTasks((prev) =>
  prev.map((task) => (task.id === id ? { ...task, title: newTitle } : task))
);
```

### 7.2 Objects

```jsx
const [profile, setProfile] = useState({ name: "Asha", city: "Pune" });

// ✅ Copy the object, change one property
setProfile((prev) => ({ ...prev, city: "Mumbai" }));
```

### 7.3 Nested objects

Spread copies only one level. Every level you change must be copied.

```jsx
const [user, setUser] = useState({
  name: "Asha",
  address: { city: "Pune", pin: "411001" }
});

// ❌ Mutation
user.address.city = "Mumbai";
setUser(user);

// ✅ Copy each level that changes
setUser((prev) => ({
  ...prev,
  address: { ...prev.address, city: "Mumbai" }
}));
```

Tip: deeply nested state is hard to update. Prefer flatter state when you can.

### 7.4 Why use the function form `setX(prev => ...)`?

When the new state depends on the old state, the function form always receives the latest value. It avoids bugs when several updates happen close together.

```jsx
// Both lines read the same stale `count`: result is +1, not +2
setCount(count + 1);
setCount(count + 1);

// Each call receives the latest value: result is +2
setCount((c) => c + 1);
setCount((c) => c + 1);
```

## 8. Unique IDs for Items

For lists that can change (add, delete, reorder), each item needs a **stable, unique** `id`.

```jsx
const newTask = {
  id: crypto.randomUUID(),   // built into modern browsers
  title: "Learn lifting state",
  completed: false
};
```

- `crypto.randomUUID()` works on `localhost` and HTTPS.
- Do not use the array index as `id` for lists that change.
- Do not call `Math.random()` or `crypto.randomUUID()` **during rendering** for keys. Generate the id once when the item is created.

## 9. Persisting State with `localStorage`

By default, state is lost when the page is refreshed. The browser's `localStorage` stores small strings that survive refreshes.

### 9.1 The API

```js
localStorage.setItem("name", "Asha");   // save a string
localStorage.getItem("name");           // "Asha" (or null if missing)
localStorage.removeItem("name");        // delete one key
localStorage.clear();                   // delete everything for this site
```

`localStorage` stores **strings only**. Convert arrays and objects with JSON:

```js
localStorage.setItem("tasks", JSON.stringify(tasks));   // object → string
const tasks = JSON.parse(localStorage.getItem("tasks")); // string → object
```

### 9.2 Reading on startup: the lazy initialiser

```jsx
function loadTasks() {
  try {
    const saved = localStorage.getItem("tasks-v1");
    return saved ? JSON.parse(saved) : [];
  } catch {
    return [];            // corrupted data should not crash the app
  }
}

const [tasks, setTasks] = useState(loadTasks); // note: no parentheses
```

Passing the **function** `loadTasks` (not `loadTasks()`) means React runs it **only on the first render**. If you wrote `useState(loadTasks())`, the function would run on every render, which wastes work.

### 9.3 Saving when state changes

```jsx
useEffect(() => {
  localStorage.setItem("tasks-v1", JSON.stringify(tasks));
}, [tasks]);
```

The effect runs after every render in which `tasks` changed.

### 9.4 Safety notes

- Never store passwords, tokens for real production apps, or personal data carelessly. Anyone using the browser can read `localStorage`.
- Wrap `JSON.parse` in `try/catch`.
- Use a versioned key such as `tasks-v1` so you can change the data shape later.
- Storage is limited (about 5 MB).

## 10. Introduction to `useRef`

`useRef` returns an object that stays the same between renders: `{ current: ... }`.

```jsx
import { useRef } from "react";

const inputRef = useRef(null);
```

It has two main uses.

### 10.1 Use 1: Access a DOM element

```jsx
import { useRef } from "react";

function SearchBox() {
  const inputRef = useRef(null);

  function focusInput() {
    inputRef.current.focus();
  }

  return (
    <div>
      <input ref={inputRef} placeholder="Type here" />
      <button onClick={focusInput}>Focus the input</button>
    </div>
  );
}
```

Common uses: focus an input, scroll to an element, play or pause a video, measure an element.

### 10.2 Focus after an action

```jsx
function TaskForm({ onAddTask }) {
  const [title, setTitle] = useState("");
  const inputRef = useRef(null);

  function handleSubmit(event) {
    event.preventDefault();
    if (!title.trim()) return;

    onAddTask(title.trim());
    setTitle("");
    inputRef.current.focus();   // ready for the next task
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        ref={inputRef}
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="New task"
      />
      <button type="submit">Add</button>
    </form>
  );
}
```

### 10.3 Use 2: Store a value that should NOT cause a re-render

```jsx
function RenderCounter() {
  const renders = useRef(0);
  renders.current += 1;          // changing a ref does not re-render

  return <p>Rendered {renders.current} times</p>;
}
```

Another common case is storing a timer id so you can clear it later:

```jsx
const timerId = useRef(null);
timerId.current = setTimeout(() => {}, 1000);
clearTimeout(timerId.current);
```

### 10.4 `useState` vs `useRef`

| | `useState` | `useRef` |
|---|---|---|
| Changing it re-renders the component | Yes | No |
| Value read in JSX output | Yes | Avoid |
| Value read in event handlers or effects | Yes | Yes |
| Typical use | Data shown on screen | DOM access, timers, "previous value" |

> **Rule:** If the screen must update when the value changes, use state. If not, a ref may be better.

**Warning:** Do not read or write `ref.current` during rendering (except for the first-time setup). Use refs in event handlers and effects.

## 11. Complete Example: Task Manager

This is the example project for the day. We will use **lifted state**, **immutable updates**, **derived data**, **localStorage**, and **useRef** together.

### 11.1 Component tree

```text

├── TaskForm      (owns: title input; calls onAddTask)
├── TaskFilter    (receives: filter, onChange)
├── TaskStats     (receives: tasks → derived counts)
└── TaskList      (receives: visible tasks + callbacks)
    └── TaskItem  (owns: isEditing and draft title)
```

### 11.3 `App.jsx`

```jsx
import { useEffect, useState } from "react";
import TaskForm from "./components/TaskForm";
import TaskFilter from "./components/TaskFilter";
import TaskStats from "./components/TaskStats";
import TaskList from "./components/TaskList";

const STORAGE_KEY = "tasks-v1";

function loadTasks() {
  try {
    const saved = localStorage.getItem(STORAGE_KEY);
    return saved ? JSON.parse(saved) : [];
  } catch {
    return [];
  }
}

function App() {
  const [tasks, setTasks] = useState(loadTasks);
  const [filter, setFilter] = useState("all"); // "all" | "active" | "completed"

  // Save whenever tasks change
  useEffect(() => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(tasks));
  }, [tasks]);

  function addTask(title) {
    const newTask = { id: crypto.randomUUID(), title, completed: false };
    setTasks((prev) => [newTask, ...prev]);
  }

  function toggleTask(id) {
    setTasks((prev) =>
      prev.map((task) =>
        task.id === id ? { ...task, completed: !task.completed } : task
      )
    );
  }

  function editTask(id, title) {
    setTasks((prev) =>
      prev.map((task) => (task.id === id ? { ...task, title } : task))
    );
  }

  function deleteTask(id) {
    setTasks((prev) => prev.filter((task) => task.id !== id));
  }

  function clearCompleted() {
    setTasks((prev) => prev.filter((task) => !task.completed));
  }

  // Derived data: NOT stored in state
  const visibleTasks = tasks.filter((task) => {
    if (filter === "active") return !task.completed;
    if (filter === "completed") return task.completed;
    return true;
  });

  return (
    <main className="container">
      <h1>Task Manager</h1>

      <TaskForm onAddTask={addTask} />
      <TaskFilter filter={filter} onFilterChange={setFilter} />
      <TaskStats tasks={tasks} onClearCompleted={clearCompleted} />

      <TaskList
        tasks={visibleTasks}
        onToggle={toggleTask}
        onEdit={editTask}
        onDelete={deleteTask}
      />
    </main>
  );
}

export default App;
```

### 11.4 `components/TaskForm.jsx`

```jsx
import { useRef, useState } from "react";

function TaskForm({ onAddTask }) {
  const [title, setTitle] = useState("");
  const [error, setError] = useState("");
  const inputRef = useRef(null);

  function handleSubmit(event) {
    event.preventDefault();

    const trimmed = title.trim();
    if (!trimmed) {
      setError("Task title is required.");
      inputRef.current.focus();
      return;
    }

    onAddTask(trimmed);   // event flows UP
    setTitle("");
    setError("");
    inputRef.current.focus();
  }

  return (
    <form onSubmit={handleSubmit} className="task-form">
      <label htmlFor="task-title">New task</label>
      <input
        id="task-title"
        ref={inputRef}
        value={title}
        onChange={(event) => setTitle(event.target.value)}
        placeholder="e.g. Practise lifting state"
      />
      <button type="submit">Add</button>
      {error && <p className="error">{error}</p>}
    </form>
  );
}

export default TaskForm;
```

### 11.8 `components/TaskItem.jsx`

```jsx
import { useEffect, useRef, useState } from "react";

function TaskItem({ task, onToggle, onEdit, onDelete }) {
  const [isEditing, setIsEditing] = useState(false);
  const [draft, setDraft] = useState(task.title);
  const editRef = useRef(null);

  // Focus the input when we enter edit mode
  useEffect(() => {
    if (isEditing) editRef.current.focus();
  }, [isEditing]);

  function save() {
    const trimmed = draft.trim();
    if (trimmed) onEdit(task.id, trimmed);
    else setDraft(task.title);        // ignore empty edits
    setIsEditing(false);
  }

  function handleKeyDown(event) {
    if (event.key === "Enter") save();
    if (event.key === "Escape") {
      setDraft(task.title);
      setIsEditing(false);
    }
  }

  return (
    <li className={task.completed ? "task done" : "task"}>
      <input
        type="checkbox"
        checked={task.completed}
        onChange={() => onToggle(task.id)}
        aria-label={`Mark "${task.title}" as completed`}
      />

      {isEditing ? (
        <input
          ref={editRef}
          value={draft}
          onChange={(event) => setDraft(event.target.value)}
          onKeyDown={handleKeyDown}
          onBlur={save}
        />
      ) : (
        <span onDoubleClick={() => setIsEditing(true)}>{task.title}</span>
      )}

      <button onClick={() => setIsEditing(true)}>Edit</button>
      <button onClick={() => onDelete(task.id)}>Delete</button>
    </li>
  );
}

export default TaskItem;
```

### 11.10 Things students should notice

- Only `App` knows the full `tasks` array. Children never change it directly.
- `visibleTasks`, `completed` and `remaining` are **derived**, not stored.
- Every update creates a **new** array (`map`, `filter`, spread).
- `TaskItem` has its **own** local state (`isEditing`, `draft`) because no other component needs it. That is the correct decision.
- `useRef` is used to focus inputs. It does not re-render the component.

## 12. Common Mistakes

### Mistake 1: Mutating state

```jsx
function addTask(title) {
  tasks.push({ id: 1, title });   // ❌
  setTasks(tasks);                // same reference, React may skip the update
}
```

Fix: `setTasks((prev) => [...prev, { id: crypto.randomUUID(), title }])`.

### Mistake 2: Duplicating state

Storing `filteredTasks` in state as well as `tasks` and `filter` leads to out-of-sync data. Calculate it while rendering.

### Mistake 3: Calling the callback during render

```jsx
<button onClick={onDelete(task.id)}>Delete</button>       // ❌ runs immediately
<button onClick={() => onDelete(task.id)}>Delete</button> // ✅
```

### Mistake 4: Passing the result of the lazy initialiser

```jsx
useState(loadTasks())   // ❌ runs every render
useState(loadTasks)     // ✅ runs once
```

### Mistake 5: Forgetting `JSON.stringify` / `JSON.parse`

```js
localStorage.setItem("tasks", tasks);   // ❌ saves "[object Object]"
```

### Mistake 6: Putting state too high

If only `TaskItem` needs `isEditing`, do not store it in `App`. Keep state as close as possible to where it is used, but no lower than the closest common parent of all components that need it.

### Mistake 7: Using `useRef` for data that appears on screen

Changing `ref.current` does not update the UI. Use `useState` for anything displayed.
