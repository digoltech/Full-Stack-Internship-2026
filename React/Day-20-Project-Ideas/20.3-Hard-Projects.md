# 20.3 — Hard Projects (7 Projects)

**Level:** Advanced · **Time per project:** 4–8+ weeks · **Goal:** Plan, build, test, secure, and operate a realistic multi-feature product.

Read [20.0 — Project Guide and Standards](20.0-Project-Guide-and-Standards.md) and complete at least one Easy and one Medium project first. Hard projects are deliberately broad: define a small, testable first release, then add scope in milestones. A finished MVP is better than a large unfinished clone.

### What “Hard” means here

- Multiple user roles, complex workflows, or real-time interactions.
- A backend/database, or a clear and honest simulation of one.
- Security, data ownership, and failure cases are part of the design.
- Integration and accessibility testing in addition to component tests.
- Production-minded deployment, monitoring, and documentation.

### Scope rule

Build only the **core user journey** for version 1. Treat stretch goals as later milestones. Do not add real payments, sensitive records, or public user content without appropriate backend controls, provider setup, moderation, and privacy review.

## Project 1 — Collaborative Project Management App

### Definition

A multi-user workspace where a team creates projects, assigns tasks, tracks status, and collaborates on updates.

### What You Will Build

Implement workspaces and projects with boards or task lists. A task includes title, description, assignee, status, priority, and due date. Users can comment and filter tasks. Use a backend with authentication and enforce workspace membership and permissions server-side. Start with one board and a small set of roles before adding multiple views.

### Use Cases

- A small team organizes work and assigns ownership.
- A member filters to tasks assigned to them or due soon.
- A project owner reviews progress and changes task status.

### Suggested Features

- Authentication, workspace membership, and role-based permissions.
- Create/edit/archive projects and tasks.
- Board columns with keyboard-accessible status controls.
- Filters, sorting, due-date indicators, and task detail panel.
- Comments/activity history with clear author and timestamp.
- Optimistic updates with rollback and visible failure feedback.
- Audit ownership checks and test unauthorized access paths.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · React Router · TanStack Query · Supabase/PostgreSQL or Node/Express/MongoDB · Vitest + RTL + Playwright

### References

- Database authorization: [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Drag and drop: [dnd-kit](https://dndkit.com/) (support keyboard operation)
- Optimistic updates: [TanStack Query — Optimistic Updates](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates)
- UI inspiration: [Dribbble — project management](https://dribbble.com/tags/project-management) · [Mobbin](https://mobbin.com/)
- End-to-end tests: [Playwright](https://playwright.dev/docs/intro)

### Stretch Goals

- Multiple board/list/calendar views.
- Real-time collaboration with presence.
- Notifications with user preferences.

## Project 2 — Real-Time Chat and Community

### Definition

A community app with authenticated users, topic-based rooms, real-time messages, and basic moderation controls.

### What You Will Build

Create a channel list and message view. Members can send text messages, edit or delete their own messages, and see new messages without refreshing. Add pagination for message history, loading/reconnect states, and a basic report/mute workflow. Use a managed realtime service or a WebSocket backend. Establish authorization, input limits, and rate limits on the server before making rooms public.

### Use Cases

- A team discusses work in separate topic rooms.
- A community member joins a discussion and reads recent history.
- A moderator removes abusive content and manages reported messages.

### Suggested Features

- Sign-in and channel membership.
- Paginated history and real-time new-message subscription.
- Send/edit/delete own messages with optimistic UI and rollback.
- Online/reconnecting/offline indicators.
- Report message and moderator-only moderation actions.
- Accessible announcements for incoming messages without stealing focus.
- Message length limits, server-side authorization, and rate limiting.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · Supabase Realtime or Socket.IO · TanStack Query · Node/Express (optional) · Vitest + RTL + Playwright

### References

- Realtime: [Supabase Realtime](https://supabase.com/docs/guides/realtime) · [Socket.IO](https://socket.io/docs/v4/)
- Accessibility: [WAI-ARIA — Feed Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/) (consider the interaction model carefully)
- Security: [OWASP — Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)
- UI inspiration: [Dribbble — chat app](https://dribbble.com/tags/chat-app) · [Mobbin](https://mobbin.com/)

### Stretch Goals

- Threaded replies and reactions.
- Search messages with permission-aware results.
- User-controlled notification preferences.

## Project 3 — Multi-Vendor Marketplace

### Definition

A marketplace where buyers browse seller listings, add products to a cart, and track demo orders, while sellers manage their own listings.

### What You Will Build

Implement buyer and seller experiences on top of a backend. Buyers search listings and place a demo order. Sellers create and update only their own listings. An admin may review flagged listings. Use a fake payment flow or a payment provider's test mode only; never process real card data in your own frontend. Keep order totals and authorization decisions on the server.

### Use Cases

- A buyer discovers items by category, price, and seller.
- A seller maintains a catalogue and tracks order status.
- An administrator removes listings that violate marketplace rules.

### Suggested Features

- Public catalogue, listing details, seller profile, cart, and order history.
- Seller dashboard with listing CRUD and image validation.
- Order workflow with status history and server-calculated totals.
- Role-based access enforced by backend policies.
- Reviews tied to verified demo orders.
- Moderation and abuse-reporting basics.
- Product and order tests for ownership boundaries.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · React Router · TanStack Query · Supabase/PostgreSQL or MERN · Object storage · Vitest + RTL + Playwright

### References

- Data access: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- Uploads: [Supabase Storage](https://supabase.com/docs/guides/storage)
- Payments testing: [Stripe Testing](https://docs.stripe.com/testing) (use test mode only)
- UI inspiration: [Dribbble — marketplace](https://dribbble.com/tags/marketplace) · [Behance](https://www.behance.net/)
- Security design: [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/)

### Stretch Goals

- Inventory reservations and cancellation rules.
- Seller analytics with date-range filters.
- Accessibility audit and performance budget for catalogue pages.

## Project 4 — Personal Finance Dashboard

### Definition

A private dashboard that imports or accepts transactions, categorizes spending, and helps a user compare budgets with actual totals.

### What You Will Build

Support manual transaction entry and a sample CSV import. Show category spending, monthly trends, and budgets. Treat financial records as sensitive: require a backend with strict per-user access controls for shared/deployed data. Do not connect real bank accounts or store credentials. Provide a clear demo dataset and a way to delete it.

### Use Cases

- A user reviews income and expenses by month.
- A user compares a category budget with actual spending.
- A user imports a CSV and corrects rows that need category mapping.

### Suggested Features

- Transaction CRUD with amount, date, category, and description.
- CSV import preview, validation errors, and explicit confirmation.
- Monthly and category filters with summary cards and charts.
- Budgets with remaining amount and accessible status labels.
- Export and delete-data controls.
- Currency formatting and date-range handling.
- Per-user authorization and data deletion tests.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · React Router · TanStack Query · Recharts · Supabase/PostgreSQL · Vitest + RTL + Playwright

### References

- CSV parsing: [Papa Parse](https://www.papaparse.com/docs)
- Charts: [Recharts](https://recharts.org/en-US/guide)
- Number formatting: [MDN — `Intl.NumberFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat)
- Database access policies: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- UI inspiration: [Dribbble — finance dashboard](https://dribbble.com/tags/finance-dashboard)

### Stretch Goals

- Recurring transaction rules.
- Budget alerts with opt-in notification settings.
- Offline-friendly entry queue with conflict handling.

## Project 5 — Healthcare Appointment Portal (Demo Only)

### Definition

A demonstration scheduling portal where a patient finds an available appointment slot and manages a mock booking.

### What You Will Build

Build a directory of fictional providers, appointment availability, and a booking flow using entirely synthetic data. Show timezone and cancellation information clearly. Do **not** collect real medical details, diagnose users, or use real patient information. If authentication is included, explain that the demo is not a healthcare service and is not suitable for protected health information.

### Use Cases

- A demo user filters fictional providers by specialty and availability.
- A demo user books, reschedules, or cancels an appointment.
- A reviewer checks slot conflict handling, form accessibility, and privacy-conscious defaults.

### Suggested Features

- Fictional provider directory and profile pages.
- Date/time slot selection with timezone displayed.
- Booking confirmation, reschedule, and cancellation flows.
- Prevent double booking on the server.
- Keep forms minimal; use synthetic profile data only.
- Accessible date/time controls and clear error messages.
- Explicit demo disclaimer and no real health data.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · React Router · React Hook Form + Zod · Supabase or mock backend · Vitest + RTL + Playwright

### References

- Forms: [WAI — Forms Tutorial](https://www.w3.org/WAI/tutorials/forms/)
- Date handling: [date-fns](https://date-fns.org/docs/Getting-Started)
- Date picker accessibility: [WAI-ARIA APG — Date Picker](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/)
- UI inspiration: [Dribbble — appointment booking](https://dribbble.com/tags/appointment-booking)
- Privacy overview: [OWASP — User Privacy Protection Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/User_Privacy_Protection_Cheat_Sheet.html)

### Stretch Goals

- Provider availability management.
- Email confirmation using a sandbox provider.
- Automated tests for timezone boundaries and conflicting bookings.

## Project 6 — Headless CMS and Publishing Workflow

### Definition

A content publishing system where authors create drafts, editors review them, and readers see only published articles.

### What You Will Build

Create a public article site and a protected author/editor workspace. Articles move through draft, review, and published states. Add a rich-text or Markdown editor with safe rendering, preview, tags, and scheduled publishing as a later milestone. Enforce permissions and publication status in backend queries and policies—not only by hiding buttons.

### Use Cases

- An author drafts an article and submits it for review.
- An editor requests changes or publishes approved content.
- A reader browses published articles and opens a shareable detail link.

### Suggested Features

- Public listing, article detail, and search routes.
- Authenticated editor with role-specific actions.
- Draft/review/published workflow and revision history.
- Preview mode with sanitized content rendering.
- Tags, pagination, and SEO metadata.
- Test that drafts are not visible to anonymous readers.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · React Router · Supabase/PostgreSQL or a headless CMS · Markdown tooling · Vitest + RTL + Playwright

## Project 7 — Analytics Dashboard with Custom Reports

### Definition

A data dashboard where users explore a supplied dataset, build a report from filters, and export a useful result.

### What You Will Build

Use synthetic or open data such as public transit, environmental, or sample sales data. Create a dashboard with date-range and category filters, summary metrics, charts, and a table. Let the user save report configurations and export filtered data. Document the source and limitations; do not imply that sample data is live business intelligence.

### Use Cases

- An analyst compares a metric across dates or categories.
- A manager saves a recurring view and shares its filter URL.
- A reviewer checks data transformations, chart accessibility, loading, and large-list performance.

### Suggested Features

- Dashboard summary metrics with clear units and date ranges.
- At least two chart types and an accessible table alternative.
- Filters reflected in URL query parameters.
- Save, rename, and delete report configurations.
- CSV export for the currently filtered dataset.
- Pagination or virtualization for large tables.
- Data-source citation and an explanation of calculations.

### Tech Stack

React · Vite · TypeScript · Tailwind CSS · React Router · TanStack Query · Recharts or Visx · Papa Parse · Vitest + RTL + Playwright

### References

- Charting: [Recharts](https://recharts.org/en-US/guide) · [Visx](https://airbnb.io/visx/)
- Data tables: [TanStack Table](https://tanstack.com/table/latest)

## Hard Level — Delivery Milestones

Avoid building the entire product in one pass. Ship in these milestones:

1. **MVP:** One critical user journey, fake/synthetic data if appropriate, deployed preview.
2. **Data and states:** Backend persistence, validation, loading/error/empty states, and ownership rules.
3. **Secondary features:** Search, filters, collaboration, or reports—only if they support the core users.
4. **Quality:** Automated tests, accessibility review, responsive checks, and error handling.
5. **Release:** Production deployment, monitoring/error reporting, README, screenshots, and a known-limitations section.

## Hard Level — Submission Checklist

- [ ] All Medium-level expectations from [20.2](20.2-Medium-Projects.md#medium-level--submission-checklist).
- [ ] MVP scope and user roles are written down before implementation.
- [ ] User data is protected by backend authorization and ownership rules.
- [ ] Secrets and private keys are never placed in the frontend bundle or repository.
- [ ] Critical user journeys have integration or end-to-end coverage.
- [ ] Failure, retry, duplicate-submit, and permission-denied paths are considered.
- [ ] Accessibility and mobile behavior have been checked.
- [ ] README includes architecture overview, setup, environment variables, tests, deploy, and limitations.
- [ ] A reviewer can access a safe demo account or synthetic dataset without real personal data.

**Remember:** A hard project is not a project with the most features. It is a project where the important features work reliably and you can explain the trade-offs.
