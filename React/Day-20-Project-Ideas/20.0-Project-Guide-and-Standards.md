# 20.0 — Project Guide and Standards

**Read this file completely before you open any project idea.**

This is the "how to build" file. The three project files (`20.1-Easy-Projects.md`, `20.2-Medium-Projects.md`, `20.3-Hard-Projects.md`) are the "what to build" files. If you skip this file, you will build something that *works on your laptop* but does not look like a professional project — and that is exactly what interviewers and reviewers notice.

---

## 1. Why Projects Matter More Than Notes

You have spent 19 days learning React. Nobody can see that.

- A recruiter sees your **GitHub profile**.
- A hiring manager sees your **live link** and your **README**.
- An interviewer sees your **code** and asks about your **decisions**.

A project is the only proof that you can take a concept, a deadline, and a blank folder and turn them into something a real user can open. That is why this day exists.

**Rule of thumb:** 3 finished, polished, deployed projects beat 12 half-finished tutorials. Every time.

---

## 2. How to Choose a Project

Do not pick the "coolest" idea. Pick the one you can **finish**.

Use this checklist before you start:

| Question | Good answer |
| --- | --- |
| Can I explain the main user flow in one sentence? | "A user searches a recipe, opens it, and saves it to favourites." |
| Do I already know 70% of the tech needed? | Yes — the other 30% is what you will learn. |
| Can I build a working version in the time I have? | Yes, even if it is ugly at first. |
| Does it have at least one real data interaction? | Yes — fetch, create, filter, or save something. |
| Would I actually use this app? | Ideally yes. |

If you answer "no" to two or more, choose a smaller project.

### Recommended path

1. Finish **one Easy project** end-to-end (deployed, README, screenshots).
2. Finish **one Medium project** end-to-end.
3. Attempt **one Hard project** — but only after the first two are live.

Do not start three projects at once. A finished small project teaches more than three abandoned big ones.

## 3. The Tech Stack

### 3.1 Core stack (use this by default)

| Layer | Tool | Why |
| --- | --- | --- |
| Build tool | **Vite** | Fast, simple, the current React default. |
| UI library | **React 18+** | Function components and hooks only. |
| Language | **JavaScript (ES2022+)** | TypeScript is optional — see 3.2. |
| Styling | **Tailwind CSS** | Fast iteration, consistent spacing, no CSS naming debates. |
| Routing | **React Router v6+** | Standard client-side routing. |
| Server state | **TanStack Query (React Query)** | Caching, loading/error states, refetching — without hand-written `useEffect` fetch code. |
| Forms | **React Hook Form** (+ **Zod** for validation) | Less re-rendering, clean validation. |
| Global UI state | **Context + `useReducer`** | You already learned this on Day 10. |
| Icons | **lucide-react** | Clean, consistent, tree-shakeable. |
| Animation | **Framer Motion** (only where it helps) | Small, purposeful motion. |
| Notifications | **sonner** or **react-hot-toast** | Simple toasts. |
| Dates | **date-fns** | Smaller and tree-shakeable than Moment. |
| Testing | **Vitest + React Testing Library** | Fast, Vite-native. |
| Linting | **ESLint + Prettier** | Consistent code, fewer review comments. |
| Deployment | **Vercel** or **Netlify** | Free, Git-connected, instant previews. |

### 3.2 When to use TypeScript

Use **TypeScript** if:

- The project has more than ~10 components, or
- It has shared data shapes used in many places (e\.g\. dashboards, forms with many fields), or
- You want it on your resume (it is a strong signal).

Stay on **JavaScript** if you are still getting comfortable with React and want to ship faster. Both are acceptable. **Do not mix** JS and TS randomly in one project.

### 3.3 Backend options (pick one, do not build three)

| Option | Best for | Effort |
| --- | --- | --- |
| **Mock API** (JSON file + `json-server`, or MSW) | Easy projects, UI focus | Very low |
| **Public API** (see section 9) | Easy/Medium, real data | Low |
| **Supabase** or **Firebase** | Medium/Hard, auth + database fast | Medium |
| **Node + Express + MongoDB (MERN)** | Hard, you want full-stack proof | High |
| **Local only** (`localStorage`) | Easy, offline-first demos | Very low |

**Important:** A frontend project with `localStorage` is a *valid* project if the README says so honestly. A frontend project that *pretends* to have a backend is not.

## 4. Quality Standards (What "Done" Means)

A project is not done when it "works on your machine". It is done when a stranger can use it without asking you a question.

### 4.1 The Definition of Done

- [ ] Deployed to a public URL (Vercel/Netlify).
- [ ] Works on a fresh browser with no console errors.
- [ ] Works on mobile width (375px) and desktop width (1440px).
- [ ] Every button does something (or is visibly disabled with a reason).
- [ ] Loading, empty, error, and success states exist for every data view.
- [ ] Forms validate input and show clear messages.
- [ ] Keyboard-only navigation works for the main flow.
- [ ] Images have `alt` text; colour contrast is readable.
- [ ] README explains what it is, how to run it, and what you learned.
- [ ] At least 3 screenshots or a short GIF in the README.
- [ ] No `console.log` left in production code.
- [ ] No commented-out dead code blocks.
- [ ] No secrets, API keys, or `.env` files committed.

### 4.2 The Four States Rule

Every place that shows data must handle **four** states. This is the single most common thing juniors forget.

```text
1. Loading  → skeleton or spinner
2. Empty    → "No results yet" + a helpful action
3. Error    → what went wrong + a retry button
4. Success  → the actual data
```

If you only build state 4, your project is 25% done.

### 4.3 Accessibility Basics (non-negotiable)

- Use real `<button>` for actions and `<a>` for navigation.
- Every input has a `<label>` (or `aria-label`).
- Images have meaningful `alt` (or `alt=""` if decorative).
- Focus is visible — never `outline: none` without a replacement.
- Colour is not the only way to show meaning (add an icon or text).
- Modals trap focus and close on `Escape`.
- Page has one `<h1>` and a logical heading order.

### 4.4 Performance Basics

- Images: correct size, `loading="lazy"` below the fold, `width`/`height` set.
- No giant libraries for tiny jobs (check bundle size before installing).
- Lists over ~100 items: consider pagination or virtualization.
- Debounce search inputs (300ms).
- Code-split routes with `React.lazy` + `Suspense` in Medium/Hard projects.

### 4.5 Code Quality

- Components do **one** thing. If a file is over ~200 lines, split it.
- No business logic inside JSX. Extract to functions or hooks.
- Custom hooks for reused logic (`useLocalStorage`, `useDebounce`, `useFetch`).
- Consistent naming: `PascalCase` components, `camelCase` variables, `UPPER_SNAKE` constants.
- No magic numbers or hard-coded strings in multiple places — use constants.
- Every `useEffect` has a correct dependency array and a cleanup if needed.

## 5. Folder Structure

Use the same structure for every project. Consistency is a professional habit.

```text
my-project/
├── public/
│   └── favicon.svg
├── src/
│   ├── assets/              # images, fonts, static files imported by code
│   ├── components/
│   │   ├── ui/              # Button, Input, Modal, Card, Spinner (reusable, dumb)
│   │   └── layout/          # Navbar, Sidebar, Footer, PageWrapper
│   ├── features/            # feature-based folders (recommended for Medium/Hard)
│   │   ├── recipes/
│   │   │   ├── components/
│   │   │   ├── hooks/
│   │   │   ├── api.js
│   │   │   └── utils.js
│   │   └── favourites/
│   ├── pages/               # one file per route (Home, Detail, NotFound)
│   ├── hooks/               # shared custom hooks
│   ├── context/             # React Context providers
│   ├── lib/                 # helpers: api client, formatters, validators
│   ├── constants/           # routes, config, static lists
│   ├── styles/              # global CSS / Tailwind entry
│   ├── App.jsx
│   └── main.jsx
├── tests/                   # or colocated *.test.jsx files
├── .env.example             # variable names only, no real values
├── .gitignore
├── eslint.config.js
├── index.html
├── package.json
├── README.md
└── vite.config.js
```

### Rules

- **`components/ui`** = generic, reusable, no app knowledge. A `Button` does not know about recipes.
- **`features/*`** = app knowledge. A `RecipeCard` knows what a recipe is.
- **`pages`** = route-level composition. Pages assemble features; they do not contain heavy logic.
- **`lib`** = pure functions and API clients. Easy to test.
- **Never** put everything in one `components` folder for a Medium/Hard project.

## 6. Git and Commit Standards

### 6.1 Branching

```text
main        → always deployable
dev         → integration branch (optional for solo projects)
feat/xyz    → one feature
fix/xyz     → one bug fix
chore/xyz   → tooling, config, docs
```

For solo projects, `main` + short-lived feature branches is enough. Never commit directly to `main` once the project is deployed.

### 6.2 Commit Messages — Conventional Commits

```text
<type>(<scope>): <short description>
```

| Type | Use for |
| --- | --- |
| `feat` | A new feature |
| `fix` | A bug fix |
| `docs` | README, comments |
| `style` | Formatting, no logic change |
| `refactor` | Code change that is not a feature or fix |
| `perf` | Performance improvement |
| `test` | Adding or fixing tests |
| `chore` | Build, deps, config |
| `ci` | CI/CD changes |

**Good examples**

```text
feat(search): add debounced recipe search
fix(cart): prevent negative quantity on decrement
docs(readme): add setup steps and screenshots
refactor(api): extract fetch wrapper into lib/api.js
test(recipe-card): cover empty ingredients state
chore(deps): upgrade react-router to v6.26
```

**Bad examples**

```text
update
fixed stuff
final
asdf
changes
```

### 6.3 Commit Rules

- One logical change per commit.
- Commit message describes **why**, the diff shows **what**.
- Never commit `node_modules`, `.env`, build output, or editor folders.
- Commit at least once per working session — a green commit history shows real progress.

### 6.4 `.gitignore` (minimum)

```gitignore
node_modules
dist
build
.env
.env.local
.env.*.local
.DS_Store
*.log
.vscode/*
!.vscode/extensions.json
```

## 8. Environment Variables

Never hard-code API keys.

```text
.env.example   → committed, contains KEY names only
.env           → NOT committed, contains real values
```

Vite only exposes variables prefixed with `VITE_`:

```js
const key = import.meta.env.VITE_API_KEY;
```

**Remember:** anything in a frontend bundle is public. A `VITE_` key is visible to users. Only use keys that are safe to expose (public/read-only APIs) or proxy requests through your own backend.

## 11. Deployment Checklist

1. `npm run build` passes with no errors.
2. `npm run preview` works locally.
3. `.env` variables are added in the hosting dashboard (Vercel → Settings → Environment Variables).
4. SPA routing works on refresh (Vercel handles this; Netlify needs a `_redirects` file).
5. Images and fonts load from the deployed URL.
6. No API key is exposed in the bundle (search the `dist` output).
7. Lighthouse score is reasonable (aim: Performance ≥ 80, Accessibility ≥ 90).
8. The live link is in the README and on your LinkedIn.

**Netlify SPA redirect** — create `public/_redirects`:

```text
/*  /index.html  200
```

## 12. Testing Expectations

| Level | Minimum tests |
| --- | --- |
| Easy | 2–3 tests: one pure function, one component render, one user interaction |
| Medium | 6–10 tests: utils, a custom hook, a form validation, a list state |
| Hard | 15+ tests: utils, hooks, components, integration flow, error handling |

Use **Vitest** + **React Testing Library**. Test behaviour, not implementation.

```jsx
// Good: tests what the user sees
expect(screen.getByRole("button", { name: /add to cart/i })).toBeInTheDocument();

// Bad: tests internal state
expect(wrapper.state().isOpen).toBe(true);
```

## 14. Self-Review Checklist (Before You Submit)

### Functionality
- [ ] Every route loads without a blank screen.
- [ ] Refresh on a deep route does not 404.
- [ ] All four data states exist.
- [ ] Forms validate and show errors.
- [ ] No broken links or dead buttons.

### Code
- [ ] No `console.log` in production code.
- [ ] No unused imports or variables.
- [ ] No commented-out code blocks.
- [ ] Components under ~200 lines.
- [ ] Reused logic is in hooks or `lib`.
- [ ] `key` props are stable (not array index for reorderable lists).

### Git
- [ ] Meaningful commit history (10+ commits for a real project).
- [ ] Conventional commit messages.
- [ ] `.gitignore` excludes `node_modules`, `.env`, `dist`.
- [ ] No secrets in history.

### Docs
- [ ] README has description, live link, screenshots, setup, scripts.
- [ ] `.env.example` lists required variables.
- [ ] Known limitations are stated honestly.

### UX
- [ ] Mobile layout works at 375px.
- [ ] Focus states are visible.
- [ ] Loading is not a frozen screen.
- [ ] Errors are human-readable, not raw stack traces.

## 15. Common Mistakes to Avoid

1. **Building the whole app before deploying.** Deploy a "Hello World" on day one. Then deploy every day.
2. **No loading state.** Users think the app is broken.
3. **Fetching in `useEffect` everywhere.** Use TanStack Query for server state.
4. **Putting server data in Context.** Context is for UI state; server state has its own cache.
5. **Giant components.** If you scroll for 30 seconds, split it.
6. **`index` as `key` in a reorderable list.** Causes wrong state and bugs.
7. **Ignoring the dependency array.** Causes infinite loops and stale data.
8. **Hard-coded API keys.** They will be scraped from your public repo.
9. **No error boundary.** One crash blanks the whole app.
10. **Copy-pasting a tutorial without understanding.** You cannot explain it in an interview.
11. **Only testing on a wide desktop screen.** Check 375px.
12. **Committing `node_modules`.** Check `.gitignore` first.
13. **"Final final v2" commit messages.** Use Conventional Commits.
14. **No README.** Reviewers will not run your app to guess what it does.
15. **Chasing features before fixing states.** A polished 5-feature app beats a broken 15-feature app.

## 16. How to Present a Project

When you share a project (LinkedIn, portfolio, interview), include:

1. **One-line pitch** — what it does and for whom.
2. **Live link** — clickable, working.
3. **Repo link** — clean history, good README.
4. **3 screenshots** — desktop, mobile, and one key interaction.
5. **Tech stack** — one line.
6. **Two decisions you made and why** — e.g. "Used TanStack Query because caching and refetching were needed in three views."
7. **One thing you would improve next** — shows self-awareness.

Example:

> **Recipe Finder** — search, filter, and save recipes from TheMealDB.
> [Live](https://...) · [Code](https://...)
> React · Vite · Tailwind · TanStack Query · React Router
> I debounced search to 300ms to cut API calls by ~70%, and cached recipe details for 5 minutes so back-navigation was instant.
> Next: add offline support with a service worker.

## 17. Evaluation Rubric

Use this to score yourself honestly before submitting.

| Area | Weight | What good looks like |
| --- | --- | --- |
| Core functionality | 30% | The main user flow works reliably |
| State handling | 15% | Loading, empty, error, success all handled |
| Code quality | 15% | Small components, hooks, no dead code |
| UI / responsiveness | 15% | Clean layout at 375px and 1440px |

**Passing bar:** 70%+. **Portfolio-ready:** 85%+.
