# 19.4 — Performance Testing and Budgets

**Goal:** Turn performance into a repeatable part of development, testing, and release rather than a last-minute cleanup.

## 1. A Practical Optimization Loop

1. **Choose a user journey:** for example, open the product list, search, and open a detail page.
2. **Measure a production build:** record environment and repeat the run.
3. **Find a bottleneck:** use Lighthouse, browser Performance, Network, and React DevTools as appropriate.
4. **Form one hypothesis:** identify what work or resource causes the delay.
5. **Make one focused change:** avoid combining many optimizations in one experiment.
6. **Measure again:** compare under the same conditions.
7. **Check regressions:** functionality, accessibility, layout stability, and maintainability.

An optimization is successful only if it improves the measured user experience without breaking another important quality.

## 2. Match the Tool to the Question

| Question | Useful tool |
| --- | --- |
| Is the page's overall loading experience poor? | Lighthouse or PageSpeed Insights |
| Which asset is slow or oversized? | Browser Network panel |
| What blocks the main thread during interaction? | Browser Performance panel |
| Which React components rendered during an action? | React DevTools Profiler |
| Are real users experiencing a regression? | Field/Core Web Vitals monitoring |
| Is the production bundle unexpectedly large? | Bundler analyzer for the project's build tool |

Tools reveal evidence, not automatic fixes. Validate suggestions against how the application works.

## 3. Set a Performance Budget

A performance budget is a limit or target that helps a team notice regressions. It might cover JavaScript size for an initial route, number of requests, image transfer size, LCP, or a task's response time.

Choose budgets based on the product, audience, devices, and baseline. A budget should be measurable in CI or release checks where practical, and reviewed when the product's needs change. Avoid adopting a random number without knowing what the users and route require.

## 4. Observe Metrics in a Real Application

The `web-vitals` package can report Core Web Vitals measurements to an analytics endpoint. Install it with:

```bash
npm install web-vitals
```

A minimal reporting function might look like this:

```js
import { onCLS, onINP, onLCP } from 'web-vitals';

function reportVital(metric) {
  // Send only the fields needed by your analytics endpoint.
  const payload = {
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    id: metric.id,
  };
  navigator.sendBeacon('/analytics/vitals', JSON.stringify(payload));
}

export function startVitalsReporting() {
  onCLS(reportVital);
  onINP(reportVital);
  onLCP(reportVital);
}
```

Adapt transport, privacy, sampling, and endpoint behavior to the application. Do not send personal data with performance events. Confirm the endpoint accepts the payload and that failures do not disrupt the app.

## 5. Avoid Misleading Tests

- Do not compare development mode with production mode.
- Do not compare results from different device/network conditions as if they were identical.
- Do not treat a one-off score as a stable trend.
- Do not remove useful functionality solely to improve a synthetic score.
- Do not optimize the JavaScript bundle if the bottleneck is server response or a large image.
- Do not ignore low-end mobile devices because desktop tests look good.

## 6. Release Checklist

- [ ] Important routes and interactions have a recorded baseline.
- [ ] Production build is tested on representative viewport/device conditions.
- [ ] LCP, INP, and CLS are the metrics used for current Core Web Vitals work.
- [ ] Large images have appropriate dimensions, formats, and loading priority.
- [ ] Heavy routes or features are split only where this improves the user journey.
- [ ] A slow interaction was checked with a browser performance trace.
- [ ] Keyboard and assistive-technology behavior still works.
- [ ] Monitoring avoids personal data and does not interfere with rendering.
- [ ] The team has a process for reviewing regressions.

## Key Terms

- **Performance budget:** a measurable limit or target used to prevent regressions.
- **Main thread:** the browser thread responsible for much of JavaScript execution, style, layout, and event handling.
- **Field metric:** a measurement collected from real user sessions rather than a controlled lab run.
- **Regression:** a previously working quality, such as load speed or interaction response, getting worse.
