# Day 4.2 — JavaScript Runtime, Event Loop, and Task Queues

## Learning Objectives

By the end of this session, students should understand:

- How JavaScript executes code using the call stack.
- The roles of the JavaScript engine and runtime environment.
- How synchronous and asynchronous operations differ.
- How the event loop, task queue, and microtask queue work.
- Why Promises and timers execute in different orders.
- How to predict execution order and debug asynchronous code.

## 1. How JavaScript Executes Code

JavaScript is commonly described as single-threaded when discussing ordinary execution of JavaScript code. It executes one piece of JavaScript at a time on a given thread.

Consider:

```javascript
console.log("First");
console.log("Second");
console.log("Third");
```

**Output:**

```text
First
Second
Third
```

Each statement executes in sequence. JavaScript does not move to the next synchronous statement until the current one finishes.

To understand asynchronous JavaScript, we first need to understand the JavaScript engine and runtime.

### JavaScript Engine

A JavaScript engine executes JavaScript code. Examples include V8, used by Chrome and Node.js, and JavaScriptCore, used by Safari.

The engine handles tasks such as parsing, compiling or interpreting code, and executing it.

### Runtime Environment

The runtime provides capabilities around the engine.

In a browser, these include:

- Timers such as `setTimeout()`.
- Browser events.
- Network APIs such as `fetch()`.
- The DOM APIs.
- Mechanisms for scheduling callbacks.

In Node.js, the runtime provides different APIs, including file-system operations, networking, timers, and its event loop.

**Important:** The JavaScript engine and the runtime environment are related, but they are not the same thing.

## 2. The Call Stack

The call stack tracks function calls currently being executed. JavaScript pushes a function onto the stack when it begins executing that function and removes it when the function returns.

```javascript
function first() {
  console.log("Inside first");
  second();
}

function second() {
  console.log("Inside second");
}

console.log("Start");
first();
console.log("End");
```

**Output:**

```text
Start
Inside first
Inside second
End
```

The execution sequence is:

1. `console.log("Start")` executes.
2. `first()` is called and added to the call stack.
3. `second()` is called from inside `first()`.
4. `second()` finishes and is removed from the stack.
5. `first()` finishes and is removed from the stack.
6. The final message prints.

### Visualizing the Call Stack

When `second()` is running, the stack conceptually looks like this:

```text
┌──────────────────────┐
│ second()             │  ← Currently executing
├──────────────────────┤
│ first()              │
├──────────────────────┤
│ Global execution     │
└──────────────────────┘
```

The stack follows **Last In, First Out (LIFO)**: the most recently called function finishes before the function that called it can continue.

## 3. Synchronous and Asynchronous Operations

### Synchronous Execution

A synchronous operation completes its current execution before the next statement runs.

```javascript
console.log("A");
console.log("B");
console.log("C");
```

Output: `A`, `B`, `C`.

### Asynchronous Execution

Some operations can be scheduled to complete later, allowing the current JavaScript execution to continue.

```javascript
console.log("A");

setTimeout(() => {
  console.log("B");
}, 1000);

console.log("C");
```

Output:

```text
A
C
B
```

The timer schedules a callback. The current synchronous code continues, and the callback runs later when it is eligible to execute.

**Important:** `setTimeout(callback, 1000)` does not guarantee that the callback runs exactly one second later. It specifies a minimum delay before the callback becomes eligible to run.

## 4. What Happens Inside the Runtime?

Consider:

```javascript
console.log("Start");

setTimeout(() => {
  console.log("Timer finished");
}, 1000);

console.log("End");
```

The simplified execution sequence is:

1. JavaScript prints `Start`.
2. It registers the timer with the runtime.
3. JavaScript continues executing the current script.
4. It prints `End`.
5. After the timer delay, the callback becomes eligible to run.
6. The event loop can allow the callback to execute when the JavaScript thread is available and higher-priority queued work has been processed.

The timer does not need to keep the call stack occupied while waiting.

**Remember:** The runtime handles or coordinates asynchronous operations. The callback still needs to execute as JavaScript when it is scheduled.

## 5. What Is the Event Loop?

The event loop coordinates the execution of queued work with the JavaScript call stack.

In simplified terms, it helps determine when eligible callbacks and queued jobs can execute.

A useful conceptual model is:

```text
 JavaScript code
       |
       v
  Call Stack
       |
       | Stack becomes empty
       v
  Event Loop
       |
       +----> Microtask Queue
       |
       +----> Task Queue
       |
       v
 Execute eligible queued work
```

This diagram is simplified. Browsers have more detailed scheduling rules, and rendering may occur between tasks.

For ordinary browser JavaScript:

- The current synchronous execution runs first.
- Promise reactions and other microtasks are processed at microtask checkpoints.
- Timer callbacks and many event callbacks run as tasks.
- The browser may perform rendering work between tasks.

The event loop does not mean JavaScript executes all operations simultaneously. It coordinates when queued JavaScript work gets an opportunity to execute.

## 6. The Task Queue (Macrotasks)

A **task**, often informally called a macrotask, is a unit of work scheduled by the host runtime.

Common examples include:

- Timer callbacks from `setTimeout()`.
- Many browser event callbacks, such as click handlers.
- Some message and I/O-related callbacks, depending on the environment.

Example:

```javascript
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");
```

Output:

```text
A
C
B
```

Even with a delay of `0`, the timer callback does not interrupt the current synchronous code. It runs later as a scheduled task.

The exact timing depends on the runtime and its scheduling rules.

## 7. The Microtask Queue

Microtasks are used for certain high-priority jobs that should be processed at microtask checkpoints.

Common examples include:

- Promise `.then()` callbacks.
- Promise `.catch()` and `.finally()` callbacks.
- `queueMicrotask()` callbacks.
- Certain asynchronous language jobs, including continuation after `await`.

Example:

```javascript
console.log("Start");

Promise.resolve().then(() => {
  console.log("Promise callback");
});

console.log("End");
```

Output:

```text
Start
End
Promise callback
```

The Promise callback does not interrupt the current synchronous code. It runs after the current synchronous execution reaches a microtask checkpoint.

### Microtasks Versus Tasks

When both a Promise callback and a timer callback are scheduled during the same synchronous execution, the Promise callback generally runs first in the browser example below.

```javascript
console.log("Start");

setTimeout(() => {
  console.log("Timer");
}, 0);

Promise.resolve().then(() => {
  console.log("Promise");
});

console.log("End");
```

**Output:**

```text
Start
End
Promise
Timer
```

Why?

1. `Start` prints.
2. The timer callback is scheduled as a task.
3. The Promise reaction is scheduled as a microtask.
4. `End` prints.
5. The current synchronous execution finishes.
6. The microtask runs.
7. The timer task runs when eligible.

**Key rule for these examples:** After the current synchronous script finishes, queued microtasks are processed before the next ordinary task is selected. Microtasks can also enqueue more microtasks, which are processed at the same checkpoint before the next task proceeds.

## 8. Understanding `queueMicrotask()`

JavaScript provides `queueMicrotask()` to schedule a callback as a microtask.

```javascript
console.log("A");

queueMicrotask(() => {
  console.log("B");
});

Promise.resolve().then(() => {
  console.log("C");
});

console.log("D");
```

**Output:**

```text
A
D
B
C
```

The two microtasks were scheduled in that order, so `B` executes before `C`.

`queueMicrotask()` is useful when code needs to run after the current synchronous work but before the next task.

## 9. Nested Microtasks and Timers

Predict the output:

```javascript
console.log("Start");

setTimeout(() => {
  console.log("Timer 1");

  Promise.resolve().then(() => {
    console.log("Promise inside Timer 1");
  });
}, 0);

Promise.resolve().then(() => {
  console.log("Promise 1");

  Promise.resolve().then(() => {
    console.log("Promise 2");
  });
});

console.log("End");
```

**Output:**

```text
Start
End
Promise 1
Promise 2
Timer 1
Promise inside Timer 1
```

The initial Promise reaction and its nested Promise reaction are processed before the timer task. When the timer callback runs, it schedules another Promise reaction, which is processed at the next microtask checkpoint.

This demonstrates why nested asynchronous operations require careful tracing.

## 10. How `async/await` Fits into the Event Loop

An async function executes synchronously until it reaches an `await` that suspends its execution.

```javascript
async function example() {
  console.log("A");

  await Promise.resolve();

  console.log("B");
}

console.log("Start");

example();

console.log("End");
```

**Output:**

```text
Start
A
End
B
```

The steps are:

1. `Start` prints.
2. `example()` begins running.
3. `A` prints before the `await`.
4. The async function suspends while waiting for the Promise.
5. The surrounding code continues, so `End` prints.
6. The function resumes through a scheduled continuation and prints `B`.

An `await` does not block the entire JavaScript thread. It suspends the surrounding async function until the awaited value settles.

## 11. Browser Rendering and Long-Running JavaScript

The browser also needs time to update the screen, process input, and perform rendering work.

Consider:

```javascript
console.log("Start");

const end = Date.now() + 2000;

while (Date.now() < end) {
  // Blocking the main JavaScript thread
}

console.log("End");
```

This loop blocks the main JavaScript thread for roughly two seconds. During that time, the page may not respond smoothly to user interactions or render updates.

A timer or Promise cannot make a long synchronous loop automatically non-blocking.

For CPU-heavy work, consider breaking work into smaller chunks or using a Web Worker when suitable.

## 12. Browser Event Loop Versus Node.js

The browser and Node.js both execute JavaScript with event-loop-based asynchronous behavior, but their host APIs and scheduling details differ.

For example:

- Browsers provide DOM events and rendering-related scheduling.
- Node.js provides server-side APIs such as file-system operations and networking.
- Node.js has event-loop phases and also supports `process.nextTick()`, which has distinct scheduling behavior.
- Exact ordering between some timer and I/O callbacks can depend on the environment and version.

For this internship, students should first master the general model of call stack, synchronous execution, Promise microtasks, and scheduled tasks. Node.js-specific event-loop details can be studied further when backend development begins.
