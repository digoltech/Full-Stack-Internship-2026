# 18.2 — Server State with TanStack Query

**Goal:** Fetch, display, cache, and update remote data with TanStack Query while handling every important request state.

## 1. What Is Server State?

Server state is data owned by a server that the UI reads or changes: users, products, messages, or bookings. It has different needs from local UI state because it can be stale, fail to load, be shared across screens, and change outside the current component.

TanStack Query manages server-state concerns such as caching, loading and error states, refetching, and keeping queries in sync after mutations. It does not replace local state for things like an open menu or current input text.

## 2. Install and Add the Provider

```bash
npm install @tanstack/react-query
```

Create the client once outside the component so it is not recreated on every render. Put its provider near the application root:

```jsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: 1,
    },
  },
});

export function AppProviders({ children }) {
  return (
    <QueryClientProvider client={queryClient}>
      {children}
    </QueryClientProvider>
  );
}
```

`staleTime` is how long fetched data is considered fresh for automatic refetch decisions. It does not mean the cached data is deleted after that time.

## 3. Create a Fetch Function

Keep request and response handling in a service function rather than repeating it in every component:

```js
export async function getUsers({ signal }) {
  const response = await fetch('/api/users', { signal });
  if (!response.ok) {
    throw new Error(`Could not load users (${response.status}).`);
  }
  return response.json();
}
```

`fetch()` does not reject for HTTP error statuses such as 404 or 500. Check `response.ok` and throw so the query enters its error state. The supplied `signal` allows an obsolete request to be cancelled.

## 4. Read Data with `useQuery`

```jsx
import { useQuery } from '@tanstack/react-query';
import { getUsers } from '../services/users.js';

export function UsersPage() {
  const usersQuery = useQuery({
    queryKey: ['users'],
    queryFn: ({ signal }) => getUsers({ signal }),
  });

  if (usersQuery.isPending) return <p role="status">Loading users…</p>;
  if (usersQuery.isError) {
    return <p role="alert">{usersQuery.error.message}</p>;
  }
  if (usersQuery.data.length === 0) return <p>No users yet.</p>;

  return (
    <ul>
      {usersQuery.data.map((user) => (
        <li key={user.id}>{user.name} — {user.email}</li>
      ))}
    </ul>
  );
}
```

### Query Keys Matter

A query key identifies the data in the cache. Use an array and include every variable that changes the result:

```js
['users', { search, page }]
```

If the search term or page changes, the key changes and the correct result is cached separately. Do not put non-serializable objects or secrets in a key.

## 5. Update Data with a Mutation

```jsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

function useCreateUser() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async (newUser) => {
      const response = await fetch('/api/users', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(newUser),
      });
      if (!response.ok) throw new Error('Could not create the user.');
      return response.json();
    },
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['users'] });
    },
  });
}
```

Use the mutation in a component:

```jsx
const createUser = useCreateUser();

async function handleCreate(values) {
  await createUser.mutateAsync(values);
}
```

Invalidating the `users` query marks it stale and lets the active view refresh. You can also update cached data directly, but that requires careful handling of data shape and race conditions.

## 6. Loading, Refetching, and Errors

- **Initial pending state:** there is no data to show yet; show a loading indicator or skeleton.
- **Background fetching:** cached data may remain visible while a refresh runs; indicate refresh without replacing useful content unnecessarily.
- **Error:** explain what failed and provide a retry action where appropriate.
- **Empty:** a successful response with no records is not a network error.
- **Mutation error:** keep the user’s input when possible and explain how to recover.

For retry buttons, call the query's `refetch()` method. Avoid retrying every error forever; some failures require user action or authentication.

## 7. When Not to Use It

Do not add a server-state library for a single static value without a clear need. Do not use it as a general replacement for all React state. It is most valuable when the application has remote data that needs caching, synchronization, invalidation, or consistent request states.

## Practice

Add a search input and include its value in the query key. Make the API function accept the search term. Test loading, failed request, empty results, and successful results.
