#  — Day 10.1: Custom Hooks, Performance Basics and Error Boundaries

## 1. Learning Objectives

By the end of this session, students should be able to:

- Explain what a custom hook is and why we create one.
- State the Rules of Hooks and explain why they exist.
- Build reusable hooks: `useToggle`, `useLocalStorage`, `useDebounce`, `useFetch`.
- Refactor repeated component logic into hooks.
- Explain **when** React re-renders a component.
- Use `useMemo`, `useCallback` and `React.memo` correctly, and explain when **not** to use them.
- Memoise a Context `value` to avoid needless re-renders.
- Use the React DevTools Profiler to find and prove a performance problem.
- Add an **Error Boundary** so that one crashing component does not blank the whole app.
- Use lazy loading for pages with `React.lazy` and `Suspense` (introduction).

## 2. Recap

In Days 5–9 we copied this pattern many times:

```jsx
const [data, setData] = useState(null);

const [error, setError] = useState("");

```

Repeating code is a sign that we need a **custom hook**.

## 3. What Is a Custom Hook?

A **custom hook** is a JavaScript function that:

1. has a name starting with **`use`** (`useFetch`, `useToggle`), and
2. calls **other hooks** (`useState`, `useEffect`...) inside it.

It lets you **reuse stateful logic** (not UI). Each component that calls the hook gets **its own separate copy of the state**.

```text
Component A ── useToggle() ──▶ own state: true
Component B ── useToggle() ──▶ own state: false     (not shared!)
```

> If you need to **share** state between components, use lifting or Context (Day 5, Day 9). Custom hooks share **logic**, not data.

### Component vs hook

| Component | Custom hook |
|---|---|
| Returns JSX | Returns anything (values, functions, objects, arrays) |
| Name starts with a capital letter | Name starts with `use` |
| Used as `<Card />` | Called as `useToggle()` |

## 4. Rules of Hooks

1. Call hooks **only at the top level** of a component or custom hook. Not inside `if`, loops, nested functions or after an early `return`.
2. Call hooks **only from React functions** (components and custom hooks), not from regular JavaScript functions or event handlers.

```jsx
// ❌ conditional hook
if (isLoggedIn) {
  const [name, setName] = useState("");
}

// ❌ after an early return
if (loading) return <Loader />;
const [x, setX] = useState(0);

// ✅ always the same hooks in the same order
const [name, setName] = useState("");
if (!isLoggedIn) return null;
```

**Why?** React identifies each hook by **the order** in which it is called during a render. If the order changes between renders, React gives state to the wrong hook. The ESLint plugin `eslint-plugin-react-hooks` (already in the Vite template) catches these mistakes. **Read its warnings. Do not silence them.**

## 5. Hook 1: `useToggle`

### Before

```jsx
const [isOpen, setIsOpen] = useState(false);
// ...
<button onClick={() => setIsOpen((open) => !open)}>Menu</button>
```

### Hook

```jsx
// hooks/useToggle.js
import { useState } from "react";

export function useToggle(initialValue = false) {
  const [value, setValue] = useState(initialValue);

  function toggle() {
    setValue((current) => !current);
  }

  return [value, toggle, setValue];
}
```

### Usage

```jsx
const [isOpen, toggleOpen] = useToggle();
const [showPassword, toggleShowPassword] = useToggle(false);
```

Returning an **array** lets the caller choose names (like `useState`). Return an **object** when you have many values.

## 6. Hook 2: `useLocalStorage`

This replaces the pattern we wrote in Day 5 (tasks), Day 8 (sort preference) and Day 9 (theme).

```jsx
// hooks/useLocalStorage.js
import { useEffect, useState } from "react";

export function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const saved = localStorage.getItem(key);
      return saved !== null ? JSON.parse(saved) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      localStorage.setItem(key, JSON.stringify(value));
    } catch {
      // storage may be full or blocked (private mode): ignore silently
    }
  }, [key, value]);

  return [value, setValue];
}
```

### Usage

```jsx
const [tasks, setTasks] = useLocalStorage("tasks-v1", []);
const [sort, setSort] = useLocalStorage("sort", "price-asc");

setTasks((prev) => [...prev, newTask]);   // functional updates still work
```

The hook returns the **same shape as `useState`**, so replacing `useState` with `useLocalStorage` requires almost no other change. That is a mark of a good hook API.

## 7. Hook 3: `useDebounce` (from Day 8)

```jsx
// hooks/useDebounce.js
import { useEffect, useState } from "react";

export function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);

  return debounced;
}
```

## 8. Hook 4: `useFetch`

This hook replaces the repeated `loading / error / data / AbortController` code.

### 8.1 Design the API first

```jsx
const { data, loading, error, refetch } = useFetch("/products/1");
```

### 8.2 Implementation

```jsx
// hooks/useFetch.js
import { useCallback, useEffect, useState } from "react";
import { request } from "../services/apiClient";

export function useFetch(path) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(Boolean(path));
  const [error, setError] = useState("");
  const [reloadKey, setReloadKey] = useState(0);

  useEffect(() => {
    if (!path) return;                      // allow "skip" by passing null

    const controller = new AbortController();

    async function load() {
      try {
        setLoading(true);
        setError("");
        const result = await request(path, { signal: controller.signal });
        setData(result);
      } catch (err) {
        if (err.name !== "AbortError") setError(err.message);
      } finally {
        if (!controller.signal.aborted) setLoading(false);
      }
    }

    load();
    return () => controller.abort();
  }, [path, reloadKey]);

  const refetch = useCallback(() => setReloadKey((key) => key + 1), []);

  return { data, loading, error, refetch };
}
```

### 8.3 Usage: the details page becomes tiny

```jsx
// pages/ProductDetailsPage.jsx (Day 7 version was ~35 lines)
import { useParams } from "react-router-dom";
import { useFetch } from "../hooks/useFetch";
import Loader from "../components/Loader";
import ErrorMessage from "../components/ErrorMessage";

function ProductDetailsPage() {
  const { productId } = useParams();
  const { data: product, loading, error, refetch } = useFetch(`/products/${productId}`);

  if (loading) return <Loader />;
  if (error) return <ErrorMessage message={error} onRetry={refetch} />;

  return (
    <article>
      <h1>{product.title}</h1>
      <p>{product.description}</p>
    </article>
  );
}
```

### 8.4 Hook design tips

- Design the **call site first** (how you would like to use it), then implement.
- Keep a hook **focused**: one responsibility.
- Return values that are easy to use (`{ data, loading, error }`).
- Clean up effects (abort, clear timers, remove listeners).
- Put the dependency on **primitive values** (strings, numbers) rather than objects created during render, otherwise the effect re-runs every render.
- Know the limits: `useFetch` here has no caching or de-duplication. Libraries such as TanStack Query provide these. Learn the problem first, then the library.

## 9. More Small Hooks (Practice Ideas)

```jsx
// useOnClickOutside: close a dropdown when clicking outside
export function useOnClickOutside(ref, handler) {
  useEffect(() => {
    function listener(event) {
      if (!ref.current || ref.current.contains(event.target)) return;
      handler(event);
    }
    document.addEventListener("mousedown", listener);
    return () => document.removeEventListener("mousedown", listener);
  }, [ref, handler]);
}
```

```jsx
// useWindowWidth
export function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  return width;
}
```

```jsx
// useDocumentTitle
export function useDocumentTitle(title) {
  useEffect(() => {
    const previous = document.title;
    document.title = title;
    return () => { document.title = previous; };
  }, [title]);
}
```

## 10. Performance: When Does React Re-render?

A component re-renders when:

1. Its **state** changes.
2. Its **parent** re-renders (even if its props did not change!).
3. A **context** it consumes changes.

Re-rendering is **normal and usually cheap**. React is fast. A render means "call the function and compare with the previous output", not "rebuild the entire page". The DOM is updated only where something actually differs.

> **First rule of performance: measure, then optimise.** Do not add `useMemo` everywhere. It adds complexity and memory use and often does nothing.

### 10.1 A demonstration of the parent-re-render rule

```jsx
function Parent() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Clicked {count}</button>
      <ExpensiveChild />   {/* re-renders on every click, though it has no props */}
    </div>
  );
}
```

### 10.2 Tool: React DevTools Profiler

1. Install the **React Developer Tools** browser extension.
2. Open DevTools → **Profiler** tab → click **Record** → interact → **Stop**.
3. Look at the flame chart: grey components did not render; coloured ones did and show the time.
4. Settings (gear icon) → **"Highlight updates when components render"** shows a flash around re-rendering components.
5. Components tab → select a component → "Why did this render?" (enable it in Profiler settings).

### 10.3 Cheap fix 1: move state down

If only one small part needs the state, move the state into a smaller component.

```jsx
function Parent() {
  return (
    <div>
      <Counter />          {/* owns count: only Counter re-renders */}
      <ExpensiveChild />
    </div>
  );
}
```

### 10.4 Cheap fix 2: pass `children`

```jsx
function Layout({ children }) {
  const [open, setOpen] = useState(false);
  return (
    <div>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      {children}       {/* the element was created by the parent: not re-created here */}
    </div>
  );
}
```

These two fixes cost nothing and solve many problems **before** you need memoisation.

## 11. `React.memo`

`React.memo` wraps a component so that it **skips re-rendering if its props are unchanged** (compared shallowly).

```jsx
import { memo } from "react";

const ProductCard = memo(function ProductCard({ product, onAdd }) {
  console.log("render", product.id);
  return (
    <article>
      <h3>{product.title}</h3>
      <button onClick={() => onAdd(product)}>Add</button>
    </article>
  );
});

export default ProductCard;
```

### The catch: reference equality

In JavaScript `{} === {}` is `false`, and `() => {} === () => {}` is `false`. Every render creates **new** objects, arrays and functions. So this will break the memo:

```jsx
function ProductList({ products }) {
  const { addItem } = useCart();

  return products.map((p) => (
    <ProductCard
      key={p.id}
      product={p}
      onAdd={(product) => addItem(product)}   // new function every render → memo useless
    />
  ));
}
```

To benefit from `memo`, all props must be **stable**. That is the job of `useCallback` and `useMemo`.

## 12. `useCallback`: Remember a Function

```jsx
const handleAdd = useCallback((product) => {
  dispatch({ type: "ADD_ITEM", payload: product });
}, []);        // dispatch is stable, so no dependencies needed
```

- It returns the **same function** between renders as long as the dependencies do not change.
- On its own, `useCallback` does **nothing useful**. It matters only when the function is passed to a **memoised** child (`memo`), or is a dependency of another hook.

## 13. `useMemo`: Remember a Calculated Value

```jsx
const visibleProducts = useMemo(() => {
  return products
    .filter((p) => p.title.toLowerCase().includes(search.toLowerCase()))
    .sort((a, b) => a.price - b.price);
}, [products, search]);
```

- It recalculates **only** when `products` or `search` change.
- Use it for **expensive** calculations (large lists, heavy loops) or to keep an **object/array reference stable** for a memoised child or a dependency array.

### Memoising Context values (from Day 9)

```jsx
export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, initialState, init);

  const value = useMemo(() => {
    const totalItems = state.items.reduce((s, i) => s + i.quantity, 0);
    const totalPrice = state.items.reduce((s, i) => s + i.price * i.quantity, 0);

    return {
      items: state.items,
      totalItems,
      totalPrice,
      addItem: (product) => dispatch({ type: "ADD_ITEM", payload: product }),
      removeItem: (id) => dispatch({ type: "REMOVE_ITEM", payload: id }),
      increase: (id) => dispatch({ type: "INCREASE", payload: id }),
      decrease: (id) => dispatch({ type: "DECREASE", payload: id }),
      clearCart: () => dispatch({ type: "CLEAR" })
    };
  }, [state.items]);   // dispatch never changes, so it is not needed here

  return <CartContext.Provider value={value}>{children}</CartContext.Provider>;
}
```

Now, if the Provider's **parent** re-renders for an unrelated reason, the `value` object keeps the **same reference**, and consumers do not re-render.

### When to use / not to use

| Use `useMemo` / `useCallback` / `memo` when | Do not use when |
|---|---|
| The Profiler shows a real slow render | "It might be slow someday" |
| A calculation is genuinely heavy | The calculation is trivial (adding two numbers) |
| A memoised child receives the value | Nothing depends on the reference |
| It stabilises a Context value or an effect dependency | Everywhere by default |

**Note:** Modern React has a tool called the *React Compiler* that can add this memoisation automatically at build time. Even then, understanding **why** re-renders happen is essential.

## 14. Worked Example: Finding and Fixing a Slow Render

### The problem

```jsx
function ProductsPage() {
  const [search, setSearch] = useState("");
  const [cartCount, setCartCount] = useState(0);

  return (
    <>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      <button onClick={() => setCartCount((c) => c + 1)}>Cart {cartCount}</button>
      <ProductGrid products={products} />   {/* 1000 cards re-render on every key press */}
    </>
  );
}
```

### Steps

1. Record in the Profiler while typing. See `ProductGrid` and all cards in colour.
2. Fix 1: memoise the card and keep its props stable.

```jsx
const ProductCard = memo(function ProductCard({ product, onAdd }) { /* ... */ });

function ProductGrid({ products }) {
  const { addItem } = useCart();
  const handleAdd = useCallback((product) => addItem(product), [addItem]);

  return products.map((p) => <ProductCard key={p.id} product={p} onAdd={handleAdd} />);
}
```

3. Fix 2: if `ProductGrid` itself should not re-render on typing, wrap it in `memo` and keep `products` stable.
4. Record again. Grey (skipped) components = success.
5. Write down the numbers: render time before and after.

## 15. Error Boundaries

By default, an error thrown **during rendering** (for example, `product.title` when `product` is `null`) unmounts the whole app and leaves a **blank white screen**.

An **Error Boundary** catches rendering errors in its children and shows a **fallback UI** instead.

### Important facts

- Error boundaries must (still) be **class components**. There is no hook for it.
- They catch errors in rendering, lifecycle methods and constructors of their children.
- They do **not** catch errors in event handlers, in async code (`fetch`, `setTimeout`) or in the boundary itself. Use `try/catch` there.

### 15.1 A simple boundary

```jsx
// components/ErrorBoundary.jsx
import { Component } from "react";

class ErrorBoundary extends Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, info) {
    // In real apps: send to a logging service
    console.error("Caught by ErrorBoundary:", error, info.componentStack);
  }

  handleReset = () => {
    this.setState({ hasError: false, error: null });
  };

  render() {
    if (this.state.hasError) {
      return (
        <div role="alert" className="error-box">
          <h2>Something went wrong</h2>
          <p>{this.state.error?.message}</p>
          <button onClick={this.handleReset}>Try again</button>
        </div>
      );
    }

    return this.props.children;
  }
}

export default ErrorBoundary;
```

### 15.2 Where to place boundaries

```jsx
// MainLayout.jsx
<main>
  <ErrorBoundary>
    <Outlet />
  </ErrorBoundary>
</main>
```

If one page crashes, the navbar and footer still work and the user can navigate away. You can add smaller boundaries around risky widgets.

**Reset on navigation:** give the boundary a `key` that changes with the route so it resets when the user goes elsewhere: `<ErrorBoundary key={location.pathname}>`.

### 15.3 Test it

```jsx
function BrokenComponent() {
  throw new Error("I crashed on purpose");
}
```

In development, Vite shows an error overlay on top. Close it (press `Esc`) to see your fallback UI. In a production build, the fallback appears directly.

## 16. Code Splitting with `React.lazy` and `Suspense` (Introduction)

By default, Vite bundles all pages into one JavaScript file. Users download code for pages they may never visit. **Lazy loading** downloads a page's code only when it is first needed.

```jsx
// App.jsx
import { lazy, Suspense } from "react";
import { Routes, Route } from "react-router-dom";
import Loader from "./components/Loader";

const ProductsPage = lazy(() => import("./pages/ProductsPage"));
const CartPage = lazy(() => import("./pages/CartPage"));

function App() {
  return (
    <Suspense fallback={<Loader text="Loading page..." />}>
      <Routes>
        {/* ... */}
        <Route path="products" element={<ProductsPage />} />
        <Route path="cart" element={<CartPage />} />
      </Routes>
    </Suspense>
  );
}
```

- The imported page must use a **default export**.
- `Suspense` shows the `fallback` while the code downloads.
- Check the Network tab: a separate `.js` file loads when you open the page.
- Combine with an error boundary so that a failed download (offline) shows a message.

| Existing code | Replace with |
|---|---|
| `useState + useEffect` fetching in pages | `useFetch` |
| `localStorage` code in tasks, theme, favourites | `useLocalStorage` |

## 18. Common Mistakes

| Mistake | Problem | Fix |
|---|---|---|
| Hook name without `use` | Lint cannot check the rules | `useSomething` |
| Calling a hook inside a condition | State mismatch, errors | Always call at top level |
| Expecting two components to share state via the same hook | Each call has its own state | Context or lifting |
| `useMemo` on everything | Complexity, no gain | Measure first |
| `memo` + inline objects/functions as props | Memo never skips | Stabilise props |
| Missing dependencies in `useCallback` / `useMemo` | Stale values | Follow the ESLint warning |
| Object literal in a dependency array (`[{ id }]`) | Effect runs every render | Use primitives (`[id]`) |
| Expecting an Error Boundary to catch `fetch` errors | It does not | `try/catch` + error state |
| Lazy component without `Suspense` | Runtime error | Wrap in `Suspense` |
| Sharing a mutable object between renders by mistake | Bugs | Keep state immutable |
