# Week 4 — Day 14.1: Frontend Architecture and Styling Systems

**Topics:** Folder architecture, Tailwind CSS, design tokens, reusable components

## 1. Project Architecture

```text
src/
├── app/          # providers, routing and application setup
├── components/   # reusable UI components
├── features/     # feature-specific logic and components
├── hooks/        # reusable hooks
├── services/     # API clients and endpoint functions
├── utils/        # pure helpers
└── styles/       # global styles and design tokens
```

- Co-locate code that belongs to one feature.
- Keep reusable components independent of API data.
- Keep endpoint and HTTP knowledge inside services.
- Use an explicit public export when a feature is imported elsewhere.

## 2. Tailwind CSS

Tailwind can be used for utility-first, responsive styling:

```jsx
<button className="rounded-lg bg-blue-600 px-4 py-2 text-white hover:bg-blue-700">
  Save
</button>
```

- Start from one consistent spacing and color scale.
- Extract repeated utility combinations into components.
- Use responsive prefixes such as `sm:`, `md:`, and `lg:`.
- Do not rely only on color for status information.
- Verify generated CSS and remove dead utility code in production builds.

## 3. CSS Modules Alternative

CSS Modules remain valid for projects that prefer scoped traditional CSS.

- One module per component.
- Global design tokens in a shared CSS file.
- The `classNames` helper pattern for conditional modifier classes.

## 4. Git and README Quality

- Use short, meaningful commits.
- Use feature branches and pull requests for larger work.
- Separate configuration, data, logic, and presentation changes.
- Write setup, environment, architecture, testing, and deployment instructions in the README.
