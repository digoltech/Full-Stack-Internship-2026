# 19.3 — Images, Network, and Asset Delivery

**Goal:** Reduce unnecessary transfer and rendering work while protecting image quality, accessibility, and layout stability.

## 1. Images Often Dominate Page Weight

Large images can delay the main content and consume mobile data. Start by identifying which assets are actually used and how large they are. Then choose a suitable format, dimensions, and loading priority.

- Use modern formats such as AVIF or WebP when supported by the delivery pipeline, while retaining a suitable fallback when needed.
- Resize images to the largest display dimensions they actually need; do not send a huge original to a small card.
- Compress carefully and compare visual quality.
- Use a CDN or image service when it meaningfully simplifies resizing, format negotiation, or delivery.

## 2. Responsive Images

Use `srcSet` and `sizes` to let the browser select an appropriate image resource for the viewport:

```jsx
<img
  src="/images/team-800.webp"
  srcSet="/images/team-400.webp 400w, /images/team-800.webp 800w, /images/team-1200.webp 1200w"
  sizes="(max-width: 600px) 100vw, 800px"
  width="1200"
  height="800"
  alt="The product team working together at a table"
/>
```

The browser can use the layout hint in `sizes` and the available candidates to choose a resource. Real projects should verify that the generated files exist and that the chosen sizes correspond to actual display dimensions.

## 3. Lazy Loading and Priority

For an image far below the initial viewport, native lazy loading can avoid downloading it before it is needed:

```jsx
<img src="/images/customer-story.webp" loading="lazy" width="800" height="600" alt="A customer using the product" />
```

Do not lazy-load the main above-the-fold image that is likely to be the LCP element. That can delay its discovery. For a confirmed critical image, eager loading or high fetch priority may help, but use it sparingly and measure the result.

Always provide intrinsic `width` and `height` (or an equivalent reserved aspect ratio) so the browser can allocate space before the file arrives. This reduces layout shifts.

## 4. Fonts and CSS

Fonts can block or shift text if they are large or loaded late. Use only the weights and character subsets the product needs, consider self-hosting where appropriate, and set a deliberate `font-display` strategy. Verify fallback font metrics because a large difference between fallback and final fonts can cause layout shifts.

For CSS:

- Remove unused rules through the build pipeline where supported.
- Avoid loading multiple complete design systems when only a few components are needed.
- Keep critical rendering styles discoverable and avoid JavaScript-driven styling work for simple static styles.
- Be cautious with large effects such as filters, shadows, or animations over many elements.

## 5. JavaScript and Dependencies

- Use production builds with minification and compression enabled by the deployment platform.
- Inspect the bundle before replacing dependencies; measure the production output, not package reputation.
- Import only the modules and icons needed when the package supports tree-shaking.
- Split rarely visited routes and heavy tools (for example, an editor or charting feature).
- Avoid adding a dependency for a small function already provided by the platform.

Tree shaking works best with static ES module imports and packages that publish compatible modules. A package's total installed size is not the same as the code shipped to a user's browser.

## 6. Caching and Compression

Production hosting should generally compress text resources with Brotli or gzip and return appropriate cache headers. Hashed build assets can often be cached for a long time because a new file name is generated when their content changes. HTML usually needs a shorter or revalidation-based policy so users discover new deployments.

The exact headers depend on the host and whether assets are immutable. Never apply a long immutable cache policy to an asset URL whose content can change without its filename changing.

## 7. Avoid Layout Shift

Reserve space for images, embeds, ads, and async content. Use a skeleton that matches the final content's size rather than a tiny spinner that later causes everything to jump. Avoid inserting banners above content after the page is already interactive.

## Practice

Inspect one route's network panel. Identify its three largest resources, their transfer sizes and dimensions, and whether each is needed immediately. Make one image or loading-priority change, then compare LCP and CLS in repeated production tests.
