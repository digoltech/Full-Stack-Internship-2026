# 19.1 — Performance Metrics and Baselines

**Goal:** Learn what frontend performance means, measure a baseline, and choose the right optimization target.

## 1. Performance Is a User Experience

A page can be fast to download but still feel slow if it takes too long to show useful content or respond to input. Performance work asks three related questions:

- **Loading:** How soon can the user see the main content?
- **Responsiveness:** How quickly does the interface respond to a click, keypress, or tap?
- **Stability:** Does content move unexpectedly while the page loads?

Optimize the part users experience, not a single score in isolation.

## 2. Current Core Web Vitals

Core Web Vitals are field metrics used to evaluate real user experience. Current thresholds are assessed at the 75th percentile (p75):

| Metric | What it measures | Good target |
| --- | --- | --- |
| LCP — Largest Contentful Paint | Time until the largest visible text or image is rendered | 2.5 seconds or less |
| INP — Interaction to Next Paint | Responsiveness across user interactions | 200 milliseconds or less |
| CLS — Cumulative Layout Shift | Unexpected visual movement during the page lifetime | 0.1 or less |

FID (First Input Delay) is a legacy metric that has been replaced by INP as a Core Web Vital. Older articles may still discuss FID; for current responsiveness work, focus on INP.

A result just above a threshold is not a diagnosis. Find the slow route, device, interaction, or resource causing the problem first.

## 3. Lab Data and Field Data

- **Lab data** is collected in a controlled test, for example Chrome DevTools Lighthouse. It is repeatable and useful for debugging a change.
- **Field data** comes from real users and devices over time. It reveals conditions that a fast developer laptop may not reproduce.

Use lab data to investigate and compare. Use field data to understand what users actually experience. A local score is not a promise that every visitor will see the same result.

## 4. Capture a Baseline

Before changing code:

1. Choose one important route and one user task.
2. Record the browser, viewport, network/CPU conditions, and test environment.
3. Run Lighthouse in Chrome DevTools or use the browser's Performance panel.
4. Record the report and the specific bottleneck, not only the overall score.
5. Repeat the test to understand normal variation.

For a real app, test a production build. Development mode includes tooling and behavior that can distort performance results.

## 5. Find the Bottleneck

### Slow LCP

Inspect the element identified as LCP. Ask whether it is blocked by server response time, CSS/JavaScript, a late-discovered image, or font loading. Optimizing a small icon will not improve LCP if the hero image is the bottleneck.

### Poor INP

Use the Performance panel to inspect a slow interaction. Look for long JavaScript tasks, expensive event handlers, large React renders, or synchronous work. Keep event handlers focused and break up work when possible.

### High CLS

Look for images without reserved dimensions, late-inserted banners, changing font metrics, or content inserted above what the user is reading. Reserve space for expected content and avoid shifting the page after interaction.

## 6. Use a Before-and-After Record

For each change, keep a small record:

```text
Route and task:
Baseline metric and test conditions:
Observed bottleneck:
Change made:
Result after repeated production-build tests:
Trade-offs or regressions checked:
```

This prevents unrelated changes from being credited with an improvement and helps a team roll back optimizations that make code harder to maintain without measurable benefit.

## Practice

Run a Lighthouse report on one page. Write down its LCP, INP (if available in the chosen report/data), CLS, and the most actionable opportunity. Do not edit the app yet; make a diagnosis first.
