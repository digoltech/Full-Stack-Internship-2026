# 19.2 — React Rendering and Code Splitting

**Goal:** Understand what causes React work, find expensive renders, and reduce unnecessary work only when measurements support it.

## 1. What Does a Re-render Mean?

When a component's state changes, or its parent renders, React may call the component again to calculate the next UI. A render is not automatically a browser repaint and is not automatically a performance problem. React compares the new result and updates the DOM where needed.

A re-render is worth investigating when it causes measurable delay, repeated expensive calculations, or a large subtree to update unnecessarily.

Common causes include:

- State changing in a component that owns a large part of the tree.
- A parent rendering and passing newly created object or function props to memoized children.
- Expensive filtering, sorting, or calculations running on every render.
- A component subscribing to broad shared state when it needs only a small part.

## 2. Measure Before Memoizing

Use React DevTools Profiler to record a real interaction. Identify which components rendered and how long the work took. Optimize the bottleneck, then record again under the same conditions.

Do not add `memo`, `useMemo`, or `useCallback` everywhere. Memoization adds complexity and comparison work, and can hide unclear state ownership. In projects using React Compiler, the compiler may automatically optimize many common cases; follow the project's configuration and guidance rather than layering manual memoization without evidence.

## 3. Understand the Memoization Tools

- **`memo(Component)`** can skip rendering a child when its props are unchanged by shallow comparison.
- **`useMemo(calculate, dependencies)`** can reuse an expensive calculated value while dependencies remain unchanged.
- **`useCallback(function, dependencies)`** can reuse a function identity, often when passing it to a memoized child or using it as a dependency.

These tools do not make a component intrinsically fast. Dependencies must be correct, and state updates still need to happen when the UI should change.

## 4. Example: Keep an Expensive List Calculation Clear

Start with a correct derived value:

```jsx
function ProductList({ products, search }) {
  const normalizedSearch = search.trim().toLowerCase();
  const visibleProducts = products.filter((product) =>
    product.name.toLowerCase().includes(normalizedSearch)
  );

  return (
    <ul>
      {visibleProducts.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

If profiling shows this calculation is expensive and runs often, memoize it:

```jsx
import { useMemo } from 'react';

function ProductList({ products, search }) {
  const visibleProducts = useMemo(() => {
    const normalizedSearch = search.trim().toLowerCase();
    return products.filter((product) =>
      product.name.toLowerCase().includes(normalizedSearch)
    );
  }, [products, search]);

  return (
    <ul>
      {visibleProducts.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

The `products` reference and `search` value are dependencies because the result changes when either changes. If a parent creates a new `products` array each render, the memo will recalculate; fix the source of unnecessary work rather than adding more memoization blindly.

## 5. Keep Typing Responsive with `useDeferredValue`

When a user types into a search box, a large result view can be allowed to update at lower priority than the input itself:

```jsx
import { useDeferredValue, useState } from 'react';

function SearchableCatalog({ products }) {
  const [search, setSearch] = useState('');
  const deferredSearch = useDeferredValue(search);
  const isShowingOlderResults = search !== deferredSearch;
  const normalizedSearch = deferredSearch.trim().toLowerCase();
  const visibleProducts = products.filter((product) =>
    product.name.toLowerCase().includes(normalizedSearch)
  );

  return (
    <section aria-busy={isShowingOlderResults}>
      <label htmlFor="catalog-search">Search products</label>
      <input
        id="catalog-search"
        value={search}
        onChange={(event) => setSearch(event.target.value)}
      />
      {isShowingOlderResults && <p role="status">Updating results…</p>}
      <ul>
        {visibleProducts.map((product) => <li key={product.id}>{product.name}</li>)}
      </ul>
    </section>
  );
}
```

`useDeferredValue` is not a debounce and does not reduce the number of network requests. It lets React prioritize urgent updates. Use debouncing or request cancellation when the goal is to limit remote requests.

## 6. Use `useTransition` for Non-Urgent Updates

`useTransition` marks a state update as non-urgent and provides a pending indicator. It can help keep urgent input responsive while a more expensive view update is prepared:

```jsx
import { useState, useTransition } from 'react';

function CatalogControls({ categories, onCategoryChange }) {
  const [isPending, startTransition] = useTransition();
  const [category, setCategory] = useState('all');

  function selectCategory(nextCategory) {
    setCategory(nextCategory);
    startTransition(() => onCategoryChange(nextCategory));
  }

  return (
    <div aria-busy={isPending}>
      <label htmlFor="category">Category</label>
      <select id="category" value={category} onChange={(event) => selectCategory(event.target.value)}>
        {categories.map((item) => <option key={item.id} value={item.id}>{item.name}</option>)}
      </select>
      {isPending && <span role="status">Updating…</span>}
    </div>
  );
}
```

Use a transition for non-urgent rendering work, not to delay controlled text input state. It does not automatically make slow JavaScript calculations cheap.

## 7. Code Splitting

Code splitting divides a JavaScript bundle so users need not download every feature before using the first screen. Route-level splitting is often a useful starting point.

```jsx
import { lazy, Suspense } from 'react';

const ReportsPage = lazy(() => import('./pages/ReportsPage.jsx'));

export function ReportsRoute() {
  return (
    <Suspense fallback={<p role="status">Loading reports…</p>}>
      <ReportsPage />
    </Suspense>
  );
}
```

`lazy()` expects the imported module to provide a default export. Give the loading fallback a stable size when possible to reduce layout shift. A route should also handle errors from failed chunk loading, usually with an Error Boundary.

## 8. Common Pitfalls

- Memoizing every component without profiling.
- Omitting a dependency and accidentally using stale values.
- Using `useMemo` to store state or make side effects run.
- Splitting tiny components so aggressively that loading complexity outweighs savings.
- Deferring the only visible feedback, leaving users unsure whether an action worked.
- Assuming code splitting automatically improves every metric; the first screen still needs a good bundle and loading path.
